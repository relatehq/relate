# 2026-10-13: Runtime activity backbone

**Status:** design agreed and revised on 2026-10-13; not implemented. This
revision replaces the single `activity` table and event union of the earlier
draft with two record families, operations and changes, and renames two existing
tables to match. It also replaces the interim dev-server operation layer ("L3")
described in
[2026-10-07: Inspector architecture and design record](./2026-10-07-inspector.md#activity-observation).

## Outcome

One shared account of what happens in a Relate graph, usable by the Inspector,
trusted host applications and, later, authorized third-party integrations. It
answers two questions without making anyone reconstruct a timeline from domain
tables:

- **What did someone attempt?** An _operation_: one read, query, traversal,
  action invocation, receipt lookup, adoption or refresh, by one actor, with its
  outcome and the objects it touched.
- **What actually changed?** A _change_: one object created, updated, deleted or
  restored, committed atomically with the state it describes and published in a
  stable order that integrations can follow.

```ts
// Follow committed changes in publication order, resuming after a checkpoint.
const batch = await runtime.host.activity.changes.read({ cursor, limit: 100 });
for (const change of batch.entries) await processIdempotently(change);
await saveCheckpoint(batch.nextCursor);

// Browse everything that touched one customer, newest first: reads and changes.
const page = await runtime.host.activity.timeline({
  filter: {
    object: { objectDefinitionId: 'business.customer', objectId: 'cus_01' },
  },
});
```

These are proposed APIs. Operations and changes carry metadata and typed
references, never property values, filter values, action inputs/outputs, agent
code or raw errors. Receipts, object versions and current object state keep
their own tables and their own authorization. Activity is not an event-sourced
replacement for them.

## A worked example

The customer workspace example (`examples/02-customer-workspace`) has customers
from a CRM, invoices from a billing database and account reviews owned by
Relate. Ana is an account manager; Fin works in finance. IDs below are
shortened; real operation and change IDs are UUIDv7, object IDs are opaque.

### 1. Ana reads Mothlight's invoices

```ts
const ana = runtime.as(anaPrincipal);
await ana.objects.Customer.traverse.invoices('cus_01', {
  select: ['status', 'total'],
});
```

Nothing changed, so only the operations family records anything. One row in
`relate.operations`:

| column              | value                                                               |
| ------------------- | ------------------------------------------------------------------- |
| `id`                | `op_01`                                                             |
| `kind`              | `traverse`                                                          |
| `actor_kind`, `_id` | `principal`, `ana`                                                  |
| `request_id`        | `req_a1` (fresh per call for embedded callers)                      |
| `transport`         | `embedded`                                                          |
| `definition_id`     | `business.invoice` (the result object definition)                   |
| `outcome`           | `ok`                                                                |
| `started_at` … `ms` | wall-clock start/end, monotonic duration                            |
| `details`           | `{ "traversalId": "business.customer-invoices", "hasMore": false }` |

And three rows in `relate.operation_objects`, the lineage of that read:

| `operation_id` | `object_type`       | `object_key` | `role`             | `returned`                                                | `forbidden` |
| -------------- | ------------------- | ------------ | ------------------ | --------------------------------------------------------- | ----------- |
| `op_01`        | `business.customer` | `cus_01`     | `traversal-origin` | `{}`                                                      | `{}`        |

Had Fin run the same traversal, `returned` would hold only the status ID and

### 2. Ana adds a review

const receipt = await ana.actions.addAccountReview(

| `request_id`, `transport`    | `req_a2`, `embedded`                          |
| `started_at`, `completed_at` | …                                             |
| `input`, `receipt`, `reads`  | retained as today, never copied into activity |

`relate.changes`, the feed entry:

| column                 | value                                                |
| ---------------------- | ---------------------------------------------------- |
| `id`                   | `chg_01`                                             |

### 3. Ana retries the same submission

```ts
await ana.actions.addAccountReview(
  { customer: 'cus_01', note: 'Renewal call booked' },
  { idempotencyKey: 'review-2026-10-13-1' },
);
```

The runtime replays the saved receipt. No new invocation, no new change. One
best-effort row in `operations`: `op_03`, `kind = invoke`,
`outcome = succeeded`, `invocation_id = inv_a1`, `replayed = true`. A consumer
following `changes` sees nothing, which is correct: nothing changed.

### 4. The CRM renames the customer and Fin refreshes

The CRM record for Mothlight becomes "Mothlight Studio". Fin's next read
triggers a refresh, the runtime fetches the record and the store accepts the new
observation. In the acceptance transaction (`ObservationStore.accept`):

`relate.object_versions` (today `value_changes`) gets the new mapped values, as
it does today, now linked to its change:

| `change_id` | `object_type`       | `object_key` | `origin`         | `state`   | `values`                                              |
| ----------- | ------------------- | ------------ | ---------------- | --------- | ----------------------------------------------------- |
| `chg_02`    | `business.customer` | `cus_01`     | `source-refresh` | `present` | `{ "business.customer.name": "Mothlight Studio", … }` |

`relate.changes` gets the feed entry, position `42`:

| column                 | value                                       |
| ---------------------- | ------------------------------------------- |
| `id`                   | `chg_02`                                    |
| `kind`                 | `updated`                                   |
| `object_type`, `_key`  | `business.customer`, `cus_01`               |
| `changed_property_ids` | `{business.customer.name}`                  |
| `operation_id`         | `op_04` (Fin's read)                        |
| `actor_kind`, `_id`    | `principal`, `fin`                          |
| `details`              | `{ "sourceDefinitionId": "crm.customers" }` |

Fin is the actor because Fin's read observed the change. The change does not
claim Fin edited the CRM, and it does not say when the CRM changed; it says when
Relate observed it. Had the CRM returned an unchanged record, the observation
would still be accepted (freshness advances) but no version row and no change
would be written.

### 5. What a consumer sees

```ts
const batch = await runtime.host.activity.changes.read({
  cursor: afterPosition40,
});
// batch.entries:
// [{ id: 'chg_01', position: 41, kind: 'created', object: { objectDefinitionId: 'business.account-review', objectId: 'rev_01' }, invocationId: 'inv_a1', actor: { kind: 'principal', id: 'ana' }, … },
//  { id: 'chg_02', position: 42, kind: 'updated', object: { objectDefinitionId: 'business.customer', objectId: 'cus_01' }, changedPropertyIds: ['business.customer.name'], actor: { kind: 'principal', id: 'fin' }, … }]
```

A notification service reacts to `chg_01`; a cache invalidates `cus_01` on
`chg_02`; the Inspector shows `op_01` to `op_04` and both changes on one
timeline. None of them received a note, a total or a name.

## Two families, not one

| Family         | Rows                                                                      | Capture guarantee when activity is supported                                                                                      | Volume | Retention                          |
| -------------- | ------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- | ------ | ---------------------------------- |
| **Changes**    | object created, updated, deleted, restored                                | Atomic with the object state, the receipt and any version row                                                                     | low    | until explicit pruning by position |
| **Operations** | get, query, traverse, invoke (attempt or replay), receipt, adopt, refresh | Written in the committing transaction when the operation changed something; otherwise best effort, bounded, with observable drops | high   | by age, independently              |

"Atomic" means the state change and its change row both commit or both roll
back. Persistence survives normal process restart only with a persistent store;
memory provides the same atomicity but remains volatile. None of this promises
infinite retention or complete access auditing.

Keeping the families apart is what makes the guarantees cheap:

- Only `changes` takes the per-graph publication lock. Reads never do.
- `changes` prunes by position (a contiguous prefix, feed semantics preserved);
  `operations` prunes by age. Keeping a year of changes and a week of reads is
  two settings, not one.
- A feed consumer reads only changes. It never scans read traffic to find the
  next commit.
- A change carries its own actor and context snapshot, so pruning operations
  never orphans a change's provenance.

Failure to persist a required change row prevents its write from committing.
External delivery is asynchronous: a destination outage never participates in a
domain transaction. Reading existing objects and authorizing receipts do not
depend on reading activity.

The runtime defines the semantics and captures authorization-aware results.
Adapters implement atomic recording and publication ordering. A transport may
record an operation it definitively rejected before dispatch, such as
`runtime-retired`; it never fabricates engine results or committed changes.
Unknown dispatch outcomes are not described as known rejection. There is one
owner for each operation row, so transport and engine do not double-record it.

## Storage and table changes

Today's tables and what happens to each:

| Table today          | Holds                                                   | After this spec                                                                                          |
| -------------------- | ------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| `graphs`             | Installed graph and revision                            | Unchanged                                                                                                |
| `objects`            | Source-backed identity and latest observation           | Unchanged. See [open questions](#open-questions) for the later `source_objects` rename or identity split |
| `native_objects`     | Relate-owned object values and creation time            | Unchanged. Creation provenance lives in `changes` (`kind = created`), not in a `created_by` column       |
| `native_invocations` | Idempotency claim, input, receipt, actor, read evidence | **Renamed `invocations`**; gains operation, request, transport, revision and timing columns              |
| `value_changes`      | Source value history (Postgres only)                    | **Renamed `object_versions`**; gains `change_id`; later also receives native creation and update rows    |
| (dev server L3)      | In-memory operation observation                         | Replaced by `operations` and `operation_objects`                                                         |
| (new)                |                                                         | `changes`, `change_streams`, `operations`, `operation_objects`                                           |

Renames happen now because Relate has no release yet; "native" names a storage
mechanism, and the roadmap's write-back to source systems is also an invocation.
Existing rows acquire no invented actors, timestamps or historical events during
migration: new provenance columns are nullable for legacy rows only. Activity
links are references, not cascading ownership; deleting a change never deletes a
receipt, an object or a version row.

```sql
-- One row per attempt, any kind. Best effort for read-only kinds; written in
-- the committing transaction when the operation changed anything.
CREATE TABLE relate.operations (
  graph_id text NOT NULL REFERENCES relate.graphs(graph_id),
  id uuid NOT NULL,                        -- UUIDv7
  kind text NOT NULL,                      -- 'get' | 'query' | 'traverse' | 'invoke' | 'receipt' | 'adopt' | 'refresh'
  actor_kind text NOT NULL,                -- 'principal' | 'system'
  actor_id text NOT NULL,
  request_id text NOT NULL,
  transport text NOT NULL,                 -- 'embedded' | 'http' | 'mcp'
  execution_id text,
  runtime_id text,
  initiator_kind text,
  initiator_id text,
  definition_revision text NOT NULL,
  started_at timestamptz NOT NULL,
  completed_at timestamptz NOT NULL,
  duration_ms double precision NOT NULL,   -- monotonic clock
  recorded_at timestamptz NOT NULL,
  outcome text NOT NULL,                   -- 'ok' | 'not-found' | 'succeeded' | 'failed' | 'rejected' | 'uncertain'
  outcome_code text,                       -- ReadErrorCode, ActionErrorCode or a domain failure code
  definition_id text,                      -- result object definition, or the action definition
  target_type text,                        -- requested get target, retained even when absent
  target_key text,
  invocation_id text,                      -- invocation executed or replayed
  replayed boolean NOT NULL DEFAULT false,
  details jsonb NOT NULL DEFAULT '{}',     -- kind-specific: traversalId, from, hasMore
  PRIMARY KEY (graph_id, id)
);
CREATE INDEX ON relate.operations (graph_id, recorded_at);
CREATE INDEX ON relate.operations (graph_id, actor_kind, actor_id, recorded_at);
CREATE INDEX ON relate.operations (graph_id, request_id);
CREATE INDEX ON relate.operations (graph_id, invocation_id) WHERE invocation_id IS NOT NULL;

-- What an operation touched: the lineage edges.
CREATE TABLE relate.operation_objects (
  graph_id text NOT NULL,
  operation_id uuid NOT NULL,
  object_type text NOT NULL,
  object_key text NOT NULL,
  role text NOT NULL,                      -- 'target' | 'returned' | 'traversal-origin'
  returned text[] NOT NULL DEFAULT '{}',   -- stable property definition IDs
  forbidden text[] NOT NULL DEFAULT '{}',
  unavailable text[] NOT NULL DEFAULT '{}',
  PRIMARY KEY (graph_id, operation_id, object_type, object_key, role),
  FOREIGN KEY (graph_id, operation_id)
    REFERENCES relate.operations(graph_id, id) ON DELETE CASCADE
);
CREATE INDEX ON relate.operation_objects (graph_id, object_type, object_key, operation_id);

-- One row per committed change to one object.
CREATE TABLE relate.changes (
  graph_id text NOT NULL REFERENCES relate.graphs(graph_id),
  id uuid NOT NULL,                        -- UUIDv7 identity, NOT the feed cursor
  position bigint NOT NULL,                -- publication order from change_streams
  kind text NOT NULL,                      -- 'created' | 'updated' | 'deleted' | 'restored'
  object_type text NOT NULL,
  object_key text NOT NULL,
  changed_property_ids text[] NOT NULL,
  operation_id uuid NOT NULL,              -- cause; may outlive the operations row
  invocation_id text,                      -- set when caused by an action
  actor_kind text NOT NULL,
  actor_id text NOT NULL,
  context jsonb NOT NULL,                  -- OperationContext snapshot
  definition_revision text NOT NULL,
  occurred_at timestamptz NOT NULL,
  recorded_at timestamptz NOT NULL,
  details jsonb NOT NULL DEFAULT '{}',     -- sourceDefinitionId for source-origin changes
  PRIMARY KEY (graph_id, id),
  UNIQUE (graph_id, position)
);
CREATE INDEX ON relate.changes (graph_id, object_type, object_key, position);
CREATE INDEX ON relate.changes (graph_id, actor_kind, actor_id, position);
CREATE INDEX ON relate.changes (graph_id, invocation_id) WHERE invocation_id IS NOT NULL;

-- One transactional counter and retention floor per graph.
CREATE TABLE relate.change_streams (
  graph_id text PRIMARY KEY REFERENCES relate.graphs(graph_id),
  stream_id text NOT NULL,                 -- new identity only on explicit reset
  position bigint NOT NULL DEFAULT 0,      -- last committed
  floor bigint NOT NULL DEFAULT 0          -- positions at or below are pruned
);

ALTER TABLE relate.native_invocations RENAME TO invocations;
ALTER TABLE relate.invocations
  ADD COLUMN operation_id uuid,
  ADD COLUMN request_id text,
  ADD COLUMN transport text,
  ADD COLUMN definition_revision text,
  ADD COLUMN started_at timestamptz,
  ADD COLUMN completed_at timestamptz;

ALTER TABLE relate.value_changes RENAME TO object_versions;
ALTER TABLE relate.object_versions ADD COLUMN change_id uuid;
```

`change_streams` stays a separate row rather than columns on `graphs`: both
source acceptance (`packages/postgres/src/index.ts`) and native transactions
(`packages/postgres/src/native.ts`) hold `FOR SHARE` on the graphs row for the
whole transaction, and two holders upgrading to `FOR UPDATE` at commit time
would deadlock.

Memory stores keep the same two families with the same semantics and bounded
retention; memory need not gain object versions solely for activity.

### Why columns, not one JSON union

A new kind of change is a new `kind` value with the same columns: native update
and delete when they exist, merges and migrations from the history design,
future user-authored domain events. The invariants a feed relies on, one
position, one object, one cause, hold for every future kind without an extra
object index table. A new kind of operation (a sync run, a migration run, a
write-back to a source) is likewise a new `kind` with actor, context, timing and
outcome already in place. `details` is the extension slot for kind-specific
metadata; the typed columns are the truth, so there is no duplicated JSON to
validate against them.

## Record contract

Transport-safe types belong to `@relate/protocol`. Schema versions are
independent of graph definition revisions. Additive optional fields may retain a
version; incompatible semantics require a new version. Consumers must be able to
skip unsupported kinds/versions while advancing their feed checkpoint.

```ts
export type ActivityActor =
  | { readonly kind: 'principal'; readonly id: string }
  | { readonly kind: 'system'; readonly id: string };

export interface OperationContext {
  readonly requestId: string;
  readonly transport: 'embedded' | 'http' | 'mcp';
  readonly executionId?: string;
  readonly runtimeId?: string;
  /** Supplied only by trusted host attribution, never an authorization grant. */
  readonly initiator?: ActivityActor;
}

export interface ActivityObjectRef {
  readonly objectDefinitionId: string;
  readonly objectId: string;
}

export interface OperationObject extends ActivityObjectRef {
  readonly role: 'target' | 'returned' | 'traversal-origin';
  readonly returned: readonly string[]; // Stable property definition IDs.
  readonly forbidden: readonly string[];
  readonly unavailable: readonly string[];
}

export type OperationOutcome =
  | { readonly status: 'ok' | 'not-found' }
  | { readonly status: 'succeeded' }
  | { readonly status: 'failed'; readonly code: string } // domain failure
  | {
      readonly status: 'rejected';
      readonly code: ReadErrorCode | Exclude<ActionErrorCode, 'uncertain'>;
    }
  | { readonly status: 'uncertain' };

export interface Operation {
  readonly schemaVersion: 1;
  readonly id: string;
  readonly graphId: string;
  readonly definitionRevision: string;
  readonly kind:
    'get' | 'query' | 'traverse' | 'invoke' | 'receipt' | 'adopt' | 'refresh';
  readonly actor: ActivityActor;
  readonly context: OperationContext;
  readonly startedAt: string; // RFC 3339
  readonly completedAt: string;
  readonly durationMs: number;
  readonly recordedAt: string;
  readonly outcome: OperationOutcome;
  readonly definitionId?: string; // Result object definition, or the action.
  readonly target?: ActivityObjectRef; // Requested get target, even if absent.
  readonly invocationId?: string;
  readonly replayed: boolean;
  readonly objects: readonly OperationObject[];
  readonly details: {
    readonly traversalId?: string;
    readonly from?: ActivityObjectRef;
    readonly hasMore?: boolean;
  };
}

export interface Change {
  readonly schemaVersion: 1;
  readonly id: string;
  readonly position: string; // Opaque in the protocol; bigint in Postgres.
  readonly graphId: string;
  readonly definitionRevision: string;
  readonly kind: 'created' | 'updated' | 'deleted' | 'restored';
  readonly object: ActivityObjectRef;
  readonly changedPropertyIds: readonly string[];
  readonly operationId: string;
  readonly invocationId?: string;
  readonly actor: ActivityActor;
  readonly context: OperationContext;
  readonly occurredAt: string;
  readonly recordedAt: string;
  readonly details: {
    readonly sourceDefinitionId?: string; // Present for source-origin changes.
  };
  /** Present only when the adapter retains the corresponding version row. */
  readonly version?: { readonly id: string };
}
```

Rules that keep these records honest:

- The runtime assigns the authenticated principal as actor; trusted host
  operations use an explicitly supplied host actor or a named system actor.
  `initiator` can identify a person for whom an agent acts, but does not change
  the principal used for permission checks. Never infer provider authorship from
  the principal whose read triggered a refresh.
- An operation's `objects` list is derived from its typed result, never supplied
  by a consumer. It includes requested targets, returned records and traversal
  origins. A failed get retains its requested identity without asserting the
  object exists; hidden and missing objects have the same `not-found` outcome.
  Query predicates and action inputs are never mined for IDs.
- `objects` with role `returned` contains only the final page's delivered
  objects, in result order, captured after selection, authorization and
  completeness checks but before compact evidence presentation discards detail.
  Internal reads during actions or query evaluation are not separate consumer
  operations. Action authorization dependencies remain receipt storage evidence.
- Operations are recorded when they settle. A change describes the moment of the
  change inside its transaction, not the enclosing request's start. Store order
  is distinct from these wall-clock timestamps. Source-origin changes report
  when Relate observed a change; they do not establish the provider's change
  time or author.
- A `created` change lists every property the object has; an `updated` change
  lists the mapped properties whose values changed; `deleted` and `restored`
  list none. A raw provider field change alone does not produce an `updated`
  change.

## Context and causal links

```ts
// Node binding: a transport binds a trusted principal per request.
operations(principal: Principal, context?: Partial<OperationContext>): ConsumerOperations;
const ops = runtime.operations(principal, { requestId, transport: 'http' });

// Embedded callers get a fresh default request ID for EACH operation.
const alice = runtime.as(alicePrincipal);
await alice.objects.Customer.get('cus_01'); // requestId req_1, operation op_1
await alice.objects.Customer.get('cus_02'); // requestId req_2, operation op_2
```

Missing context defaults to embedded transport and a fresh request ID per call,
not per long-lived binding. Each operation also gets its own `id`. Internal work
carries that operation's context; the changes it commits share its ID.
Transports assign and forward the operation ID when they need to own a
pre-dispatch rejection. Context is snapshotted and cannot override actor or
definition revision. The engine accepts it on reads, queries, traversals,
invocations, receipt lookup and adoption.

An invocation's committed changes share its stable `invocationId`. A replay is a
new operation that refers to the original invocation and commits no change.
Neither request IDs nor invocation IDs are identity or ordering keys.

## Recording changes

### Native transactions

Extend the native transaction capability with atomic change append:

```ts
// Inside the existing native transaction, after final authorization checks.
await transaction.saveInvocation(invocation);
await transaction.appendChanges([createdReview]); // drafts: kind, object, properties
```

Drafts carry what the runtime knows: kind, object, changed property IDs,
operation, invocation, actor, context and occurrence time. The runtime assigns
stable IDs; the adapter supplies `recordedAt` and positions. `appendChanges`
stages drafts within the transaction; it participates in transaction/savepoint
rollback and handle revocation. The adapter publishes staged drafts after the
transaction callback succeeds and before COMMIT, so no user callback runs while
holding the publication lock. It is not an independent store call or an
after-commit callback. The adapter also writes the `operations` row for the
executing attempt in the same transaction.

- Success commits the invocation, the operation row and one `created` change per
  committed creation.
- A domain failure rolls back effects and commits only the failed receipt and
  its operation row; no changes.
- Known rollback produces no rows in either family.
- Replay produces no invocation or change rows. It may produce a best-effort
  operation row with `replayed: true`.
- A lost COMMIT acknowledgement leaves the operation `uncertain`. If the commit
  succeeded, its durable rows already exist. Never turn uncertainty into a known
  rejection or automatically execute the action again.

This describes Relate-owned state. External effects performed by an action are
not made transactional by a change row.

### Source acceptance

Extend `ObservationStore.accept` with trusted provenance (actor,
operation/context, occurrence time and a preassigned candidate change ID). Under
its existing acceptance lock, the adapter determines the actual winning
transition and writes the observation, any version row and the change together.
The runtime owns the semantics; the adapter does not fetch sources or evaluate
authorization.

| Accepted transition                        | Change kind | Version row (Postgres)                       |
| ------------------------------------------ | ----------- | -------------------------------------------- |
| First membership acceptance                | `created`   | `origin = adoption`                          |
| Mapped values changed, state still present | `updated`   | `origin = source-refresh`                    |
| Present to deleted                         | `deleted`   | `origin = source-refresh`, `state = deleted` |
| Deleted to present                         | `restored`  | `origin = source-refresh`                    |
| Unchanged, superseded, replay              | none        | none                                         |

Concurrent adoption/refresh uses the winning accepted state, not a diff computed
outside the transaction. A repeated acceptance does not duplicate the change.
The version reference names the row actually written, when one exists; an absent
reference means no exact historical payload is available through that change.
Memory and Postgres must agree on change semantics.

If required change persistence fails, observation acceptance fails atomically
using the existing retention failure/uncertainty contract. Whether the enclosing
read can return freshly fetched data is still governed by its existing evidence
and retention semantics; activity must not silently claim confirmed retention.

### Publication order

For the first Postgres implementation, allocate positions from the
`change_streams` row, holding its lock until commit. Allocate the batch and
insert its changes together as the final database work, after domain validation
and without provider I/O or user callbacks under the lock. Every change writer
follows this protocol and consistent lock ordering. Memory implements the
equivalent atomic append. Operations never take this lock.

This ensures that no earlier position can become visible after a later committed
position has been returned. A rolled-back transaction exposes neither its
changes nor its counter update. Do not replace this with UUID ordering or a bare
SQL sequence: allocation order alone does not establish commit visibility order.
The lock serializes a short final section per graph, which is an explicit
throughput tradeoff to measure before considering a different publisher.

The retained change log also supplies outgoing delivery; no separate outbox or
broker is required for this first implementation. A future exporter stores its
own checkpoints/delivery state outside change rows.

## Recording operations

Read-only operations use a bounded queue with limits on entries, bytes and
concurrent writes. It never awaits delivery on the consumer result path. The
runtime isolates synchronous store throws and rejected promises. It does not
claim literally zero latency or resource overhead.

Provide capture configuration, drop counters and a host error hook. Queue
overflow, write failure and shutdown abandonment are observable without trying
to report them only through the failing store. Diagnostics use sanitized failure
codes and operation kinds, not raw exception messages, IDs or values. Callback
failures must not affect operations.

A hung append occupies at most the configured concurrency; do not create
unbounded retries or new writes. Store implementations must support bounded I/O
or cancellation that releases resources. Best-effort traffic must not exhaust
the pool required by committed writes. Retry, if provided, reuses operation IDs;
append of identical IDs/payloads is idempotent and conflicting reuse rejects.

Bound individual rows as well as buffers: an operation whose `objects` list
exceeds the configured limit is recorded with a truncation marker in `details`
and counted, rather than silently claiming a complete lineage.

`close()` first drains tracked operations, then drains capture with an explicit
flush deadline. The existing Node close implementation has no such deadline;
adding it is implementation work. Deadline expiry reports abandoned capture and
must not close a host-owned shared store. Default queue sizes and flush duration
are implementation choices, exposed and tested.

## Host reading contract

Filters, pages and errors are transport-safe protocol types. Storage interfaces
in `relate` consume them, so future HTTP clients need not depend on runtime
code.

```ts
interface ActivityFilter {
  readonly actor?: ActivityActor;
  readonly objectDefinitionId?: string;
  readonly object?: ActivityObjectRef;
  readonly invocationId?: string;
  readonly operationId?: string;
  readonly requestId?: string;
  readonly from?: string; // Inclusive occurredAt/startedAt, RFC 3339.
  readonly to?: string;
}

interface ChangeFilter extends ActivityFilter {
  readonly kinds?: readonly Change['kind'][];
}

interface OperationFilter extends ActivityFilter {
  readonly kinds?: readonly Operation['kind'][];
  readonly objectRole?: OperationObject['role']; // Requires object or objectDefinitionId.
  readonly outcomes?: readonly OperationOutcome['status'][];
}

interface Page<T> {
  readonly entries: readonly T[];
  readonly nextCursor: string;
  readonly hasMore: boolean;
}

type TimelineEntry =
  | { readonly family: 'change'; readonly entry: Change }
  | { readonly family: 'operation'; readonly entry: Operation };

interface ActivityReader {
  status(): Promise<
    | { readonly state: 'unsupported' }
    | {
        readonly state: 'available';
        readonly durability: 'volatile' | 'persistent';
        readonly operationCapture: 'enabled' | 'disabled';
      }
  >;
  readonly changes: {
    /** Oldest publication first: the feed. */
    read(options?: {
      filter?: ChangeFilter;
      cursor?: string;
      limit?: number;
    }): Promise<Page<Change>>;
    /** Newest publication first: browsing. */
    list(options?: {
      filter?: ChangeFilter;
      cursor?: string;
      limit?: number;
    }): Promise<Page<Change>>;
  };
  readonly operations: {
    /** Newest recorded first; best-effort rows, no feed semantics. */
    list(options?: {
      filter?: OperationFilter;
      cursor?: string;
      limit?: number;
    }): Promise<Page<Operation>>;
  };
  /** Both families by occurrence time, newest first. For the Inspector; no feed semantics. */
  timeline(options?: {
    filter?: ActivityFilter;
    cursor?: string;
    limit?: number;
  }): Promise<Page<TimelineEntry>>;
}

// Store methods additionally take graphId; the host reader binds its graph.
interface ActivityStore {
  appendOperations(
    graphId: string,
    drafts: readonly OperationDraft[],
  ): Promise<void>;
  // status(graphId), changes.read/list(graphId, options), operations.list(graphId, options), timeline(graphId, options)
}
```

`OperationDraft` is the read-only subset without store-assigned recording time;
operations that committed changes enter through the transaction, never through
`appendOperations`.

- `changes.list` and `operations.list` return newest first. Their first page
  pins an upper bound (position or recorded time) so subsequent pages are stable
  against new appends. This is browsing, not chronological sorting by occurrence
  time.
- `changes.read` returns oldest publication first, starting at the retention
  floor when no cursor is supplied. Thereafter it returns every matching
  retained change after the checkpoint. A finite call reads to a captured
  committed high-water mark; consumers poll again to follow new appends.
- Cursors are opaque, validated and bound to graph, stream identity, method and
  normalized filter. Changed filters or a cursor from another graph/method
  reject as `invalid-cursor`. Limits default to 50 and range from 1 to 500. A
  resumed call inherits its cursor's filter when none is supplied.
- `nextCursor` describes the range scanned, including filtered-out rows. An
  empty filtered page can advance it. Never advance past unreturned matching
  rows; `hasMore` tells whether more matches remain in the call's range.
- Filters combine with AND; values within `kinds` or `outcomes` combine with OR.
  Reject contradictory object and object-definition filters. All references
  match within the bound graph. For operations, object-definition filtering
  matches lineage references and the result definition even for an empty page; a
  role filter requires a matching reference.
- Re-reading a checkpoint may return duplicates; consumers deduplicate using
  change identity and checkpoint only after successful processing. There is no
  exactly-once external side-effect guarantee.
- Unsupported activity rejects reads as `unsupported`, not an empty history.
  Store failures are `unavailable`, malformed options are `invalid-request`.
  Expired/lost stream positions are `cursor-expired`.

### Retention and restart

Memory retains the newest 10,000 changes and 10,000 operations per graph, each
with a byte bound as well. Change eviction removes a contiguous publication
prefix and advances the retention floor; operation eviction removes the oldest
recorded rows. A new memory store has a new stream identity; its old cursors
expire. Oversized committed change batches reject the associated transaction.

Postgres initially retains both families until explicit trusted pruning. Pruning
changes removes a contiguous prefix and advances the floor atomically; it never
resets/reuses positions or changes stream identity on an ordinary restart.
Pruning operations removes rows older than a given time together with their
lineage rows. A changes cursor behind the floor fails explicitly; it must not
silently skip deleted changes. Consumers then rebuild their own projection or
explicitly choose to resume from retained history. Version rows can expire
independently; resolving a missing version reference must report that absence.

Read each page, its high-water mark and its retention floor from one consistent
snapshot so concurrent pruning cannot create an undetected gap. Operation append
deduplication is guaranteed while the row is retained; retries must be bounded
to that retention window rather than resurrecting pruned history.

Automatic retention schedules and subject-specific erasure require separate
policy design. Append-only describes normal recording, not a promise that data
can never be removed. Detailed prune authorization/options are implementation
API work; the retention-floor and expired-cursor contract is required now.

## Third-party applications and data access

Only trusted host code and the Inspector can read activity initially:
`runtime.host.activity` implements `ActivityReader`. No activity methods are
added to `as(user)`, `ConsumerOperations`, MCP tools or consumer HTTP routes.

Change metadata supports notifications, timelines, cache invalidation and
triggering an authorized refresh. Fetching an object after a change returns its
current state, not necessarily its change-time state. Exact historical
applications need a retained version reference and a separately authorized
history API. A reference or change never grants permission to its payload.

Before remote exposure, define integration credentials, graph/kind scopes and
field projections. Current permission to read an object does not automatically
authorize its access history. Per-user feeds need explicit historical visibility
rules. Do not export trusted raw rows indiscriminately.

A later export adapter maps changes to CloudEvents: a stable installation/graph
URI becomes `source`, change ID becomes `id`, `relate.object.<kind>` becomes
`type`, `occurredAt` becomes `time`, and the versioned selected metadata becomes
`data`. Installation identity must distinguish independent deployments that use
the same graph ID. Preserve source/ID across retries. CloudEvents supplies an
interoperable envelope, not persistence, ordering or delivery guarantees.

Primary references verified on 2026-10-13:

- [CloudEvents 1.0.2](https://github.com/cloudevents/spec/blob/v1.0.2/cloudevents/spec.md):
  envelope and source/ID duplicate identity; optional boundary mapping, not a
  runtime dependency.
- [PostgreSQL sequence semantics](https://www.postgresql.org/docs/18/functions-sequence.html):
  sequence allocation is independent of transaction rollback; it is not the
  publication protocol.

## `relate dev` and the Inspector

1. The dev server passes context and operation identity through IPC to the
   runtime host. The runtime captures operations and committed changes.
2. After committed publication, the runtime host forwards rows to the dev
   server: `{ type: 'activity', runtimeId, changes, operations }`. Forwarding is
   best effort and never part of the native/source transaction. A feed reader
   can recover committed changes if immediate forwarding misses an
   acknowledgement.
3. The dev server deduplicates by graph/row ID and retains a bounded display
   history across runtime-host restarts. It is a development projection, not a
   durable integration checkpoint or a replacement for the store's feed.
4. L1 calls and L2 agent executions remain dev-server events and join by request
   and execution IDs. The Inspector renders operations and changes in place of
   L3, distinguishing committed changes, attempts and uncertain outcomes.
5. Delete `packages/cli/src/dev/activity/operations.ts` when runtime capture is
   connected. Keep only explicit pre-dispatch rejection capture at the routing
   boundary. Development progress/running indicators can remain transient UI
   state; they do not mutate immutable persisted rows.

Losing a memory runtime can still lose unforwarded volatile rows. Retaining a
dev-server display across saves is not a durability guarantee.

## Ownership and implementation sequence

| Location                                              | Responsibility                                                                   |
| ----------------------------------------------------- | -------------------------------------------------------------------------------- |
| `packages/protocol/src/activity.ts`                   | Context, `Operation`, `Change`, filters, pages, status and reader errors         |
| `packages/relate/src/storage.ts`                      | Activity store capability; atomic change append and source acceptance provenance |
| `packages/runtime/src/activity/`                      | Draft construction, per-operation context, operation queue and diagnostics       |
| `packages/runtime/src/actions/`, source resolution    | Emit drafts at native and observation commit boundaries                          |
| `packages/runtime/src/memory.ts`, native memory store | Atomic recording, bounded retention, stream/cursor semantics                     |
| `packages/postgres`                                   | Migrations and renames, transactional publication, indexes and pruning           |
| `packages/node/src/runtime.ts`                        | Host reader, binding context, capture configuration and bounded drain            |
| `packages/cli/src/dev/`, `apps/inspector`             | IPC/projection integration, pre-dispatch attempts and rendering                  |

Protocol remains portable; runtime depends on authoring/storage contracts, Node
composes runtime, and Postgres implements storage contracts. Inspector consumes
protocol types. Exporters consume the host reader rather than importing SQL or
becoming dependencies of runtime writes.

Implement storage/protocol guarantees first (including the two renames), then
runtime capture, then host reading and Inspector integration. Public docs,
`packages/runtime/STORE_CONTRACT.md` and store contracts must be updated with
the implementation; this design is not proof of shipped behaviour.

## Acceptance tests

- Creation, receipt, operation row and change commit together; injected
  change-write failure rolls them all back. A failed domain action records its
  terminal receipt and operation row but no rolled-back creations. Savepoint and
  revoked-handle behaviour is preserved.
- A crash after COMMIT but before response/forwarding leaves changes recoverable
  from Postgres after restart. Lost acknowledgements produce `uncertain`
  operations while committed changes remain authoritative.
- Concurrent idempotent invocations execute once; replay adds no change and
  records at most one `replayed` operation. Operation append retries deduplicate
  identical IDs and reject conflicting reuse.
- Source adoption produces one `created` change; value changes `updated`;
  tombstones `deleted`; resurrection `restored`. Concurrent refresh losers emit
  nothing, unchanged/raw-only changes emit nothing, and version references
  identify the actual accepted row. Memory/Postgres semantics agree without
  requiring memory version storage.
- Reads capture stable property IDs and distinguish forbidden/unavailable;
  compact/full evidence modes produce equivalent lineage. Hidden and missing
  gets retain the same requested target and indistinguishable outcomes.
- Query/internal reads do not over-report delivered objects. Traversal origins
  retain their own object-definition identity. No values, inputs or raw errors
  appear in any row or capture diagnostic.
- Operation write rejection, synchronous throw, hanging I/O and queue overflow
  do not change consumer results; resource bounds and drop diagnostics hold.
  Operation capture never acquires the change publication lock. Shutdown drains
  operations before bounded flushing.
- Many calls through one embedded binding get distinct default request and
  operation IDs. Transport-bound calls share request context but have distinct
  operation IDs. Retired routing records exactly one pre-dispatch operation.
- Delay an earlier change writer while a later writer runs: advancing a feed
  checkpoint cannot skip a change that commits afterwards behind it. Run this
  with multiple Postgres connections, rollback, mixed source/native writers and
  restart.
- Catch-up larger than one page returns all matches in order. Empty filtered
  scans advance safely; cursor graph/filter/method binding rejects misuse. New
  writes do not disturb pinned descending browse pages.
- Pruning operations by age leaves every change readable with its own actor and
  context. Pruning changes by position expires affected cursors explicitly.
  Memory eviction and stream replacement do the same. Persistent restart
  preserves valid cursors and IDs. Unsupported, unavailable and genuinely empty
  activity remain distinguishable.
- Legacy `invocations` and `object_versions` rows keep their keys and evidence
  with null provenance; nothing invents an operation or change for them.
- No consumer surface exposes trusted history. Inspector joins runtime rows with
  L1/L2, deduplicates forwarded rows and preserves its bounded display history
  across runtime-host restarts.

## Open questions

- **Object identity tables.** `objects` holds source-backed identity and the
  latest observation; `native_objects` holds Relate-owned values. The minimum
  coherence step is renaming `objects` to `source_objects`. The fuller step,
  which "one object enriched from several sources" needs anyway, is one
  `objects` identity table plus per-connection source aliases and observations;
  it would also let `object_versions` keep a real foreign key once native rows
  join it. Neither is part of this spec; this spec adds no activity columns to
  either table so that the later split has nothing to undo.
- **Operation rows for committing operations.** They are written in the
  transaction so a change can always join its cause. Whether a later pruning
  policy may remove them while their changes remain is left to the retention
  design; the context snapshot on `changes` makes either answer safe.
- **Adoption and refresh kinds.** `host.adopt` and a read-triggered refresh are
  two operation kinds with different actors. A sync worker run will be a third.
