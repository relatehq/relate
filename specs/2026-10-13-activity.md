# 2026-10-13: Runtime activity log

**Status:** design agreed on 2026-10-13; not implemented. It replaces the
interim dev-server operation layer ("L3") described in
[2026-10-07: Inspector architecture and design record](./2026-10-07-inspector.md#activity-observation).

## Outcome

One record of who did what, and when, in a Relate graph. It is written in one
place, the runtime engine, and read by everything that needs it:

- trusted host code, through `runtime.host.activity` (the future admin SDK);
- the Inspector, through `relate dev`;
- later, an admin HTTP surface and applications built on Relate (see
  [Not in this scope](#not-in-this-scope)).

Activity is a **log**, not domain data. It records metadata only: the actor, the
operation, the definitions and object IDs involved, the outcome and the time. It
never stores property values, action inputs or outputs.

```ts
const { entries } = await runtime.host.activity.list({
  objectId: 'cus_123',
  limit: 50,
});
// [
//   { kind: 'read', actorId: 'alice', op: 'get', objectDefinitionId: 'obj_customer',
//     objects: [{ objectId: 'cus_123', returned: ['prop_name'], withheld: ['prop_credit'] }],
//     outcome: 'ok', at: 1760350000000, ... },
//   { kind: 'invoke', actorId: 'bob', actionDefinitionId: 'act_review',
//     invocationId: 'inv_9', outcome: { status: 'succeeded' }, ... },
//   { kind: 'create', actorId: 'bob', objectDefinitionId: 'obj_review',
//     objectId: 'rev_4', invocationId: 'inv_9', ... },
// ]
```

## What exists today

| What happened            | Recorded today | Where                                                    | Why it is not activity                                                                                       |
| ------------------------ | -------------- | -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| Object read              | No             | —                                                        | Read evidence is built per response and discarded                                                            |
| Native object created    | Yes            | `relate.native_objects`                                  | `created_at` only; no actor or invocation link                                                               |
| Source value changed     | Yes            | `relate.value_changes`                                   | Changes Relate observed at the provider (`adoption`, `source-refresh`), not changes made through Relate      |
| Action invoked           | Partly         | `relate.native_invocations`                              | Replay and receipt authorization keyed by idempotency key; no timestamp; rejected attempts are never written |
| Request, MCP, agent code | In memory      | `packages/cli/src/dev/activity/` (dev server only, L1–3) | Development only, lost on exit, sees call arguments rather than what the engine returned                     |

Those tables keep their jobs. Activity entries refer to them by `invocationId`,
never copy them, and never become a dependency of replay, receipts or reads.

## Decisions

1. **Best effort.** An activity write never fails, delays or changes the
   operation it describes. A failed write is dropped and reported with
   `console.error`; nothing else.
2. **Metadata only.** Who, what, when, which objects and which property IDs. No
   values, no filter values, no action inputs or outputs.
3. **Trusted readers only.** There is no admin concept yet. Activity is readable
   through trusted host code and the Inspector, never through consumer surfaces
   (`as(user)`, `ConsumerOperations`, MCP tools, consumer HTTP routes), since
   any signed-in user could otherwise see who read which record.
4. **A log, not domain data.** Append-only. `value_changes` and
   `native_invocations` stay the source of truth for source history and action
   replay.
5. **Recorded by the runtime engine.** Only the engine knows which objects and
   properties a read returned or withheld, and which objects an action created
   and committed. Transports and the dev server pass context in; they do not
   record graph access themselves.
6. **IDs are UUIDv7.** Ordinary UUIDs that also sort by creation time, so pages
   can continue from an entry ID. Ordering between concurrent writers is
   approximate, which a best-effort log accepts.

## Entry shape

Owned by `@relate/protocol` so the Inspector, host SDK and future HTTP surface
share it.

```ts
// packages/protocol/src/activity.ts
export interface OperationContext {
  /** One transport request; several operations can share it (one MCP call). */
  readonly requestId: string;
  readonly transport: 'embedded' | 'http' | 'mcp';
  /** Present only when agent JavaScript made the call. */
  readonly executionId?: string;
  /** A `relate dev` runtime host; other hosts have none. */
  readonly runtimeId?: string;
}

interface EntryBase {
  /** UUIDv7. */
  readonly id: string;
  /** Epoch milliseconds from the runtime clock, when the operation started. */
  readonly at: number;
  readonly ms: number;
  /** `Principal.id` of the bound actor. */
  readonly actorId: string;
  readonly definitionRevision: string;
  readonly context: OperationContext;
}

/** Stable property definition IDs, never authoring names. */
export interface ActivityObject {
  readonly objectId: string;
  /** Fields delivered with a value or a known absence. */
  readonly returned: readonly string[];
  /** Selected fields not delivered: forbidden or unavailable. */
  readonly withheld: readonly string[];
}

export type ActivityEntry =
  | (EntryBase & {
      readonly kind: 'read';
      readonly op: 'get' | 'query' | 'traverse';
      readonly objectDefinitionId: string;
      /** For `traverse`: the starting object and traversal. */
      readonly from?: {
        readonly objectId: string;
        readonly traversalId: string;
      };
      /** What the caller received, in result order. Empty when nothing was. */
      readonly objects: readonly ActivityObject[];
      readonly hasMore?: boolean;
      readonly outcome: 'ok' | 'not-found' | ReadErrorCode; // ReadError codes
    })
  | (EntryBase & {
      readonly kind: 'invoke';
      readonly actionDefinitionId: string;
      /** Present when a receipt exists. */
      readonly invocationId?: string;
      /** True when the idempotency key returned an earlier receipt. */
      readonly replayed?: boolean;
      readonly outcome:
        | { readonly status: 'succeeded' }
        | { readonly status: 'failed'; readonly code: string } // domain failure
        | { readonly status: 'rejected'; readonly code: ActionErrorCode }; // ActionError codes
    })
  | (EntryBase & {
      readonly kind: 'receipt';
      readonly actionDefinitionId: string;
      readonly invocationId: string;
      readonly outcome: 'ok' | ActionErrorCode;
    })
  | (EntryBase & {
      readonly kind: 'create';
      readonly objectDefinitionId: string;
      readonly objectId: string;
      readonly invocationId: string;
    });
```

Rules:

- `not-found` is recorded as the caller saw it. A hidden object and a missing
  object both appear as `not-found`; the log does not reveal more than the
  result did.
- `create` entries are written only for records that committed. Records rolled
  back with a failed or rejected action produce no `create` entry.
- An `invoke` that replays an earlier receipt produces one `invoke` entry with
  `replayed: true` and no `create` entries.
- `query` records no filter, sort or cursor values; `objects` lists only the
  records on the returned page.
- `adopt` and other trusted host operations are not recorded in this scope.

The dev server's `OperationContext` (`apps/inspector/src/protocol.ts`) carries
`principal` and `definitionRevision` as well. In the protocol shape they move to
the entry (`actorId`, `definitionRevision`), so the context names only the
request.

## Passing context in

The engine takes an optional context on every consumer operation. The Node
binding fills it once per binding; a transport that serves one request per
binding passes its request ID.

```ts
// packages/node/src/runtime.ts
operations(principal: Principal, context?: Partial<OperationContext>): ConsumerOperations;

// embedded: each call gets its own requestId, transport 'embedded'
const alice = runtime.as(alicePrincipal);
await alice.objects.Customer.get('cus_123');

// a transport binds per request, so every operation shares the requestId
const ops = runtime.operations(principal, { requestId, transport: 'http' });
```

```ts
// packages/runtime/src/runtime.ts (engine)
read(actor, objectDefinitionId, objectId, request, context?: OperationContext)
query(actor, objectDefinitionId, request, context?)
traverse(actor, objectDefinitionId, objectId, traversal, request, context?)
invoke(actor, actionDefinitionId, request, context?)
getReceipt(actor, actionDefinitionId, invocationId, context?)
```

Missing fields default to `transport: 'embedded'` and a fresh `requestId`.

## Recording

After an operation settles (result or error), the engine builds its entries and
hands them to the store without awaiting the result path:

```ts
function record(entries: readonly ActivityEntry[]) {
  if (!store.activity) return;
  const write = store.activity.append(graphId, entries).catch((error) =>
    console.error('relate: activity entries dropped', {
      kinds: entries.map((entry) => entry.kind),
      error: error instanceof Error ? error.message : String(error),
    }),
  );
  track(write); // close() waits for pending writes, like pending operations
}
```

- The caller's result, error and latency are unchanged whether `append`
  succeeds, fails or hangs.
- An action's `invoke` and `create` entries are appended together, after the
  native transaction commits. A crash between commit and append loses them;
  `native_invocations` still holds the receipt.
- Entries for one operation are appended in one call; entries for different
  operations may interleave.
- The log line names entry kinds and the error message only, never IDs or
  values.

## Store contract

An optional capability on the store, next to `native`. It is a separate
contract, not a separate database: a source-only graph has no `NativeStore` but
still records reads, and activity must never share a transaction with domain
writes.

```ts
// packages/relate/src/storage.ts
export interface ObservationStore {
  readonly native?: NativeStore;
  /** Optional: without it, no activity is recorded. */
  readonly activity?: ActivityStore;
  // ...
}

export interface ActivityFilter {
  readonly actorId?: string;
  readonly kinds?: readonly ActivityEntry['kind'][];
  readonly objectDefinitionId?: string;
  /** Matches reads that returned it, creates of it and traversals from it. */
  readonly objectId?: string;
  readonly actionDefinitionId?: string;
  readonly invocationId?: string;
  readonly requestId?: string;
  /** Epoch milliseconds, inclusive. */
  readonly from?: number;
  readonly to?: number;
}

export interface ActivityPage {
  /** Newest first. */
  readonly entries: readonly ActivityEntry[];
  readonly hasMore: boolean;
}

export interface ActivityStore {
  /** Append-only. Never updates or deletes an entry. */
  append(graphId: string, entries: readonly ActivityEntry[]): Promise<void>;
  /** `before`: older than this entry ID; `after`: newer (for following a tail). */
  list(
    graphId: string,
    filter: ActivityFilter,
    page: { before?: string; after?: string; limit: number },
  ): Promise<ActivityPage>;
}
```

**Memory** (default, `packages/runtime/src/memory.ts`): keeps the newest 10,000
entries per graph and drops the oldest. It is volatile, like the rest of the
memory store.

**Postgres** (`packages/postgres`), one migration:

```sql
CREATE TABLE relate.activity (
  id uuid PRIMARY KEY,                -- UUIDv7
  graph_id text NOT NULL REFERENCES relate.graphs(graph_id),
  definition_revision text NOT NULL,
  at timestamptz NOT NULL,
  actor_id text NOT NULL,
  kind text NOT NULL CHECK (kind IN ('read', 'invoke', 'receipt', 'create')),
  request_id text NOT NULL,
  entry jsonb NOT NULL
);
CREATE INDEX activity_graph ON relate.activity (graph_id, id DESC);
CREATE INDEX activity_actor ON relate.activity (graph_id, actor_id, id DESC);

-- One row per object an entry touched, so "who touched cus_123" is indexed.
CREATE TABLE relate.activity_objects (
  activity_id uuid NOT NULL REFERENCES relate.activity(id),
  graph_id text NOT NULL,
  object_type text NOT NULL,
  object_key text NOT NULL,
  PRIMARY KEY (activity_id, object_type, object_key)
);
CREATE INDEX activity_objects_lookup
  ON relate.activity_objects (graph_id, object_type, object_key, activity_id DESC);
```

No retention: rows accumulate until retention is designed (see TODO).

## Reading

Trusted host code only:

```ts
// packages/node: runtime.host
runtime.host.activity.list(filter?: ActivityFilter, page?: {
  before?: string;
  after?: string;
  limit?: number; // default 50, max 500
}): Promise<ActivityPage>;
```

Without a store that has `activity`, `list` returns an empty page.

Not exposed on `as(user)`, `ConsumerOperations`, `@relate/mcp` tools or
`@relate/http` consumer routes.

## `relate dev` and the Inspector

The runtime engine runs in the runtime host, which restarts on every accepted
build. Its default memory store would lose activity at each save, so:

1. The dev server passes context with every operation it sends to the runtime
   host. The `op` request in `packages/cli/src/dev/runtime-protocol.ts` gains
   `context: OperationContext`.
2. The runtime host forwards each appended batch to the dev server in a new
   message, alongside writing it to the application's store:

   ```ts
   { type: 'activity', runtimeId: string, entries: ActivityEntry[] }
   ```

3. The dev server keeps them in its existing bounded activity log, which already
   survives runtime restarts, and streams them on `GET /dev/activity`.
4. The Inspector shows runtime entries where it shows L3 `operation` events
   today. L1 (one MCP tool call) and L2 (the JavaScript an agent ran) stay in
   the dev server and join runtime entries by `requestId` and `executionId`.
5. L3 (`packages/cli/src/dev/activity/operations.ts`) is deleted.

## Ownership

| Location                                   | Adds                                                                                                     |
| ------------------------------------------ | -------------------------------------------------------------------------------------------------------- |
| `packages/protocol/src/activity.ts`        | `OperationContext`, `ActivityEntry`, `ActivityObject`                                                    |
| `packages/relate/src/storage.ts`           | `ActivityStore`, `ActivityFilter`, `ActivityPage`; `ObservationStore.activity`                           |
| `packages/runtime/src/activity/`           | Entry building per operation, UUIDv7, best-effort `record`, context parameter on engine                  |
| `packages/runtime/src/memory.ts`           | Bounded in-memory `ActivityStore`                                                                        |
| `packages/postgres`                        | Activity migration and `ActivityStore`                                                                   |
| `packages/node/src/runtime.ts`             | `operations(principal, context?)`, `host.activity.list`                                                  |
| `packages/cli/src/dev/`                    | Context in IPC `op`, `activity` IPC message, forwarding into the dev log; L3 removed                     |
| `apps/inspector`                           | Render runtime entries in the Activity page and graph highlights; protocol types from `@relate/protocol` |
| `tests/support/activity-store-contract.ts` | Shared memory/Postgres contract tests                                                                    |

Dependency direction is unchanged: protocol ← relate ← runtime ← node/postgres ←
cli; the Inspector reads protocol types only.

## Acceptance tests

- A `get` with one forbidden field records the object with that property ID in
  `withheld`, and no value appears anywhere in the entry.
- A hidden object and a missing object record the same `not-found` entry.
- A store whose `append` rejects: the read or action returns exactly as without
  activity, and `console.error` is called once without IDs or values.
- A store whose `append` never settles: the operation still returns; `close()`
  waits for it (bounded by the existing close behavior).
- A domain-failed action records `invoke` with `status: 'failed'` and no
  `create` entries; a succeeded one records `create` for each committed record.
- A replayed idempotency key records `replayed: true` and no `create` entries.
- `denied`, `invalid` and `runtime-retired` invocations record `rejected`.
- `list` filters by actor, kind, object, action, invocation, request and time,
  pages with `before` and `after`, and returns newest first; memory and Postgres
  pass the same contract.
- No consumer surface (`as(user)`, `ConsumerOperations`, MCP tools) exposes
  activity.
- In `relate dev`, activity from before a runtime restart is still visible after
  it, and MCP calls join their runtime entries by `requestId`.
