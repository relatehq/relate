# 2026-10-13: Runtime activity backbone

**Status:** design agreed on 2026-10-13 and revised on 2026-10-18; not
implemented. This revision replaces the single `activity` table and event union
of the earlier draft with two record families, operations and the durable feed,
and renames two existing tables to match. It also replaces the interim
dev-server operation layer ("L3") described in
[2026-10-07: Inspector architecture and design record](./2026-10-07-inspector.md#activity-observation).

Revised on 2026-10-18 after review. Operation rows are always best effort; the
durable feed carries invocation completions alongside changes; adopting a source
record is distinct from creating an object; who created or adopted an object is
stored on the object itself; and a read-triggered refresh is a nested operation.
The handler identity that is stable across retries is now
`ActionContext.idempotencyId`, so "operation" means one attempt everywhere.

## Outcome

One shared account of what happens in a Relate graph, usable by the Inspector,
trusted host applications and, later, authorized third-party integrations. It
answers three questions without making anyone reconstruct a timeline from domain
tables:

- **What did someone attempt?** An _operation_: one read, query, traversal,
  action invocation, receipt lookup, adoption or refresh, by one actor, with its
  outcome and the objects it touched.
- **What actually changed?** A _change_: one object created in Relate, adopted
  from a source, updated, deleted or restored, committed atomically with the
  state it describes.
- **Which actions finished?** An _invocation event_: one action invocation that
  reached a durable receipt, succeeded or failed, committed atomically with that
  receipt.

Changes and invocation events form the _feed_: one stable publication order that
integrations can follow.

```ts
// Follow the feed in publication order, resuming after a checkpoint.
const batch = await runtime.host.activity.feed.read({ cursor, limit: 100 });
for (const entry of batch.entries) await processIdempotently(entry);
await saveCheckpoint(batch.nextCursor);

// Who created or adopted this customer? Stored on the object, always available.
const provenance = await runtime.host.activity.provenance({
  objectDefinitionId: 'business.customer',
  objectId: 'cus_01',
});

// Browse what directly references one customer, newest first: reads and feed.
const page = await runtime.host.activity.timeline({
  filter: {
    object: { objectDefinitionId: 'business.customer', objectId: 'cus_01' },
  },
});
```

These are proposed APIs. Operations and changes carry metadata and typed
references, never property values, filter values, action inputs/outputs, agent
code or raw errors. Receipts, object versions and current object state keep
their own tables and their own authorization. Activity is not an event-sourced
replacement for them.

## A worked example

The customer workspace example (`examples/02-customer-workspace`) has customers
from a CRM, invoices from a billing database and account reviews owned by
Relate. Ana is an account manager; Fin works in finance. IDs below are
shortened; real operation and change IDs are UUIDv7, object IDs are opaque.

### 1. Ana reads Mothlight's invoices

```ts
const ana = runtime.as(anaPrincipal);
await ana.objects.Customer.traverse.invoices('cus_01', {
  select: ['status', 'totalMinor'],
});
```

Nothing changed, so only the operations family records anything. One best-effort
row in `relate.operations`:

| column              | value                                                               |
| ------------------- | ------------------------------------------------------------------- |
| `id`                | `op_01`                                                             |
| `kind`              | `traverse`                                                          |
| `actor_kind`, `_id` | `principal`, `ana`                                                  |
| `request_id`        | `req_a1` (fresh per call for embedded callers)                      |
| `transport`         | `embedded`                                                          |
| `definition_id`     | `business.invoice` (the result object definition)                   |
| `outcome`           | `ok`                                                                |
| `started_at` … `ms` | wall-clock start/end, monotonic duration                            |
| `details`           | `{ "traversalId": "business.customer-invoices", "hasMore": false }` |

And three rows in `relate.operation_objects`, the lineage of that read:

| `operation_id` | `ordinal` | `object_type`       | `object_key` | `role`             | `returned`                                                | `forbidden` |
| -------------- | --------- | ------------------- | ------------ | ------------------ | --------------------------------------------------------- | ----------- |
| `op_01`        | `0`       | `business.customer` | `cus_01`     | `traversal-origin` | `{}`                                                      | `{}`        |
| `op_01`        | `1`       | `business.invoice`  | `inv_01`     | `returned`         | `{business.invoice.status, business.invoice.total-minor}` | `{}`        |
| `op_01`        | `2`       | `business.invoice`  | `inv_02`     | `returned`         | `{business.invoice.status, business.invoice.total-minor}` | `{}`        |

Had Fin run the same traversal, `returned` would hold only the status ID and
`forbidden` the total ID: the read is recorded after authorization decided the
actual result. Property values never appear.

### 2. Ana adds a review

```ts
const receipt = await ana.actions.addAccountReview({
  input: { customer: 'cus_01', note: 'Renewal call booked' },
  idempotencyKey: 'review-2026-10-13-1',
});
```

One transaction commits the new review with its creation provenance, the
receipt, one change and one invocation event. The operation row is recorded
afterwards, best effort.

`relate.native_objects` stores who created the review on the object row itself:

| column                  | value              |

| `created_invocation_id` | `inv_a1`           |
| `created_operation_id`  | `op_02`            |
| `created_at`            | …                  |

`relate.invocations` (today `native_invocations`), the durable receipt record:

| column                       | value                                         |
| ---------------------------- | --------------------------------------------- |
| `action_id`                  | `business.add-account-review`                 |
| `idempotency_key`            | `review-2026-10-13-1`                         |
| `invocation_id`              | `inv_a1`                                      |
| `actor_id`                   | `ana`                                         |
| `operation_id`               | `op_02` (the attempt that executed it)        |
| `request_id`, `transport`    | `req_a2`, `embedded`                          |
| `started_at`, `completed_at` | …                                             |
| `input`, `receipt`, `reads`  | retained as today, never copied into activity |

`relate.changes`, the feed entry:

| column                 | value                                                |
| ---------------------- | ---------------------------------------------------- |
| `id`                   | `chg_01`                                             |
| `position`             | `41` (next position of this graph's change stream)   |

| `object_type`, `_key`  | `business.account-review`, `rev_01`                  |

`relate.invocation_events`, the feed entry for the finished invocation, position

| column              | value                         |
| ------------------- | ----------------------------- |
| `id`                | `ive_01`                      |
| `kind`              | `invocation-succeeded`        |
| `action_id`         | `business.add-account-review` |

| `actor_kind`, `_id` | `principal`, `ana`            |

Once the outcome is known, the best-effort queue records `op_02` in
`relate.operations` with `kind = invoke`, `outcome = succeeded` and
`invocation_id = inv_a1`. If that row is dropped, nothing durable is lost: the
change, the invocation event and the object row each name `op_02`, Ana and the
request context themselves.

### 3. Ana retries the same submission

```ts
await ana.actions.addAccountReview({
  input: { customer: 'cus_01', note: 'Renewal call booked' },
  idempotencyKey: 'review-2026-10-13-1',
});
```

The runtime replays the saved receipt. No new invocation, change or invocation
event. One best-effort row in `operations`: `op_03`, `kind = invoke`,
`outcome = succeeded`, `invocation_id = inv_a1`, `replayed = true`. A consumer
following the feed sees nothing, which is correct: nothing new happened.

Each attempt is its own operation with a fresh ID. Had the first attempt thrown
after an external write and Ana retried, the retry would be a new operation, but
the handler would receive the same `idempotencyId` both times, so the provider
deduplicates the external write:

```ts
// attempt 1: operation op_02, handler idempotencyId 'relate-op-v1-3f9a…' (throws)
// attempt 2: operation op_03, handler idempotencyId 'relate-op-v1-3f9a…'
```

### 4. The CRM renames the customer and Fin's read refreshes it

The CRM record for Mothlight becomes "Mothlight Studio". Fin's next read,
`op_04`, finds the stored observation stale and refreshes it. The refresh is a
nested operation, `op_05`: `kind = refresh`, `parent_operation_id = op_04`,
`details.refresh = 'changed'` after confirmed acceptance. Had the observation
been fresh, there would be no `op_05`; had the CRM returned an unchanged record,
`op_05` would record `unchanged`. When the best-effort row is retained, the
Inspector can tell whether a refresh happened; a missing row is not evidence
that none happened.

The runtime fetches the record and the store accepts the new observation. In the
acceptance transaction (`ObservationStore.accept`):

`relate.object_versions` (today `value_changes`) gets the new mapped values, as
it does today, now linked to its change:

| `change_id` | `object_type`       | `object_key` | `origin`         | `state`   | `values`                                              |
| ----------- | ------------------- | ------------ | ---------------- | --------- | ----------------------------------------------------- |
| `chg_02`    | `business.customer` | `cus_01`     | `source-refresh` | `present` | `{ "business.customer.name": "Mothlight Studio", … }` |

`relate.changes` gets the feed entry, position `43`:

| column                     | value                                       |
| -------------------------- | ------------------------------------------- |
| `id`                       | `chg_02`                                    |
| `kind`                     | `updated`                                   |
| `origin`                   | `source-refresh`                            |
| `object_type`, `_key`      | `business.customer`, `cus_01`               |
| `changed_property_ids`     | `{business.customer.name}`                  |
| `operation_id`             | `op_05` (the refresh)                       |
| `parent_operation_id`      | `op_04` (Fin's read)                        |
| `actor_kind`, `_id`        | `source`, `crm.customers`                   |
| `triggered_by_kind`, `_id` | `principal`, `fin`                          |
| `details`                  | `{ "sourceDefinitionId": "crm.customers" }` |

The actor identifies the source where Relate observed the change.
`triggered_by_kind` and `triggered_by_id` preserve Fin's role in triggering that
observation even if both operation rows are dropped. `parent_operation_id` links
to the read when its row is available. None of these fields claims Fin edited
the CRM or identifies the provider's author. The change says when Relate
observed the rename, not when the CRM made it. Had the CRM returned an unchanged
record, the observation would still be accepted (freshness advances) but no
version row and no change would be written.

### 5. What a consumer sees

```ts
const batch = await runtime.host.activity.feed.read({
  cursor: afterPosition40,

// batch.entries:
// [{ id: 'chg_01', position: '41', kind: 'created', origin: 'native', object: { objectDefinitionId: 'business.account-review', objectId: 'rev_01' }, invocationId: 'inv_a1', actor: { kind: 'principal', id: 'ana' }, … },
//  { id: 'ive_01', position: '42', kind: 'invocation-succeeded', actionDefinitionId: 'business.add-account-review', invocationId: 'inv_a1', actor: { kind: 'principal', id: 'ana' }, … },
//  { id: 'chg_02', position: '43', kind: 'updated', origin: 'source-refresh', object: { objectDefinitionId: 'business.customer', objectId: 'cus_01' }, changedPropertyIds: ['business.customer.name'], actor: { kind: 'source', id: 'crm.customers' }, triggeredBy: { kind: 'principal', id: 'fin' }, parentOperationId: 'op_04', … }]
```

A notification service reacts to `chg_01` or `ive_01`; a cache invalidates
`cus_01` on `chg_02`; the Inspector shows `op_01` to `op_05`, with `op_05`
nested under Fin's read, and the feed entries on one timeline. None of them
received a note, a total or a name.

A customer timeline filtered to `cus_01` shows Ana's traversal, Fin's read, the
refresh and `chg_02`. It does not show `chg_01`: that change references the
review `rev_01`, and v1 filters match direct references only.

## Two families, not one

| Family         | Rows                                                                                                 | Capture guarantee when activity is supported                          | Volume | Retention                                  |
| -------------- | ---------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------- | ------ | ------------------------------------------ |
| **Feed**       | changes (object created, adopted, updated, deleted, restored); invocation events (succeeded, failed) | Atomic with the object state, the receipt and any version row         | low    | kept; future pruning by position           |
| **Operations** | get, query, traverse, invoke (attempt or replay), receipt, adopt, refresh                            | Best effort once the outcome is known: bounded, with observable drops | high   | kept; future pruning by age, independently |

"Atomic" means the state change and its feed entries both commit or both roll
back. Persistence survives normal process restart only with a persistent store;
memory provides the same atomicity but remains volatile. None of this promises
infinite retention or complete access auditing.

Keeping the families apart is what makes the guarantees cheap:

- Only feed writes take the per-graph publication lock. Recording an operation
  never does; a read-triggered refresh that commits a change uses the feed lock.
- There is no pruning yet. When it is added, the feed prunes by position (a
  contiguous prefix, feed semantics preserved) and operations by age, so keeping
  a year of changes and a week of reads is two settings, not one.
- A feed consumer reads only the feed. It never scans read traffic to find the
  next commit.
- A feed entry carries its own actor, context and cause, so it stands alone
  without its operation row. Source-refresh changes also snapshot the actor who
  triggered the observation.
- Who created or adopted an object is stored on the object row, so it never
  depends on activity retention.

Operation rows are never part of a committing transaction. An operation row
describes the attempt's final outcome, which the transaction cannot know: a read
can accept several source refreshes, each in its own transaction, before its
result exists, and a lost COMMIT acknowledgement makes an outcome `uncertain`
although the transaction may have committed. The feed is the durable record of
what committed; an operation row is a best-effort account of the attempt.

Best effort means operation-recording failure does not fail the caller's
operation. Operation history may have gaps: a successful read can lose its row
to queue overflow or a failed append, and a committed action can lose its row if
the process exits before flushing. With a persistent store, its required feed
entries and receipt survive restart. Drop counters and error hooks report
recording problems; they cannot reconstruct lost rows. This is diagnostic
history, not a complete access audit. Disabling operation capture does not
disable the feed or object provenance.

Failure to persist a required feed entry prevents its write from committing.
External delivery is asynchronous: a destination outage never participates in a
domain transaction. Reading existing objects and authorizing receipts do not
depend on reading activity.

The runtime defines the semantics and captures authorization-aware results.
Adapters implement atomic recording and publication ordering. A transport may
record an operation it definitively rejected before dispatch, such as
`runtime-retired`; it never fabricates engine results or committed changes.
Unknown dispatch outcomes are not described as known rejection. There is one
owner for each operation row, so transport and engine do not double-record it.

## Storage and table changes

Today's tables and what happens to each:

| Table today          | Holds                                                   | After this spec                                                                                                                                         |
| -------------------- | ------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `graphs`             | Installed graph and revision                            | Unchanged                                                                                                                                               |
| `objects`            | Source-backed identity and latest observation           | Gains adoption provenance: who adopted the record, when and through which operation. See [open questions](#open-questions) for the later identity split |
| `native_objects`     | Relate-owned object values and creation time            | Gains creation provenance: creating actor, invocation and operation. The permanent answer to "who created this?"                                        |
| `native_invocations` | Idempotency claim, input, receipt, actor, read evidence | **Renamed `invocations`**; gains operation, request, transport, revision and timing columns                                                             |
| `value_changes`      | Source value history (Postgres only)                    | **Renamed `object_versions`**; gains `change_id`; later also receives native creation and update rows                                                   |
| (dev server L3)      | In-memory operation observation                         | Replaced by `operations` and `operation_objects`                                                                                                        |
| (new)                |                                                         | `changes`, `invocation_events`, `feed_streams`, `operations`, `operation_objects`                                                                       |

Renames happen now because Relate has no release yet; "native" names a storage
mechanism, and the roadmap's write-back to source systems is also an invocation.
Existing rows acquire no invented actors, timestamps or historical events during
migration: new provenance columns are nullable for legacy rows only. Activity
links are references, not cascading ownership; deleting a feed entry never
deletes a receipt, an object or a version row.

### Store capability

Keep the capability on the existing store composition rather than introducing a
second independently committed database:

```ts
interface ObservationStore {
  readonly native?: NativeStore;
  readonly activity?: ActivityStore;
  // Existing observation operations; accept gains activity provenance.
}
```

Built-in memory and Postgres stores implement activity. Third-party adapters may
omit it, but an adapter advertising activity must support the atomic source and
native feed and provenance guarantees for every write capability it exposes. A
standalone best-effort sink cannot advertise that guarantee. Runtime setup
validates the capability combination and rejects a store that advertises
`activity` without them. Feed entries have the durability of their owning store.

```sql
-- One row per attempt, any kind. Always best effort, recorded once the outcome
-- is known; never written inside a committing transaction.
CREATE TABLE relate.operations (
  graph_id text NOT NULL REFERENCES relate.graphs(graph_id),
  id uuid NOT NULL,                        -- UUIDv7; fresh per attempt
  schema_version smallint NOT NULL,
  parent_operation_id uuid,                -- enclosing operation, e.g. the read that triggered a refresh
  kind text NOT NULL,                      -- 'get' | 'query' | 'traverse' | 'invoke' | 'receipt' | 'adopt' | 'refresh'
  actor_kind text NOT NULL,                -- 'principal' | 'system' | 'source'
  actor_id text NOT NULL,
  request_id text NOT NULL,
  transport text NOT NULL,                 -- 'embedded' | 'http' | 'mcp'
  execution_id text,
  runtime_id text,
  initiator_kind text,
  initiator_id text,
  definition_revision text NOT NULL,
  started_at timestamptz NOT NULL,
  completed_at timestamptz NOT NULL,
  duration_ms double precision NOT NULL,   -- monotonic clock
  recorded_at timestamptz NOT NULL,
  outcome text NOT NULL,                   -- 'ok' | 'not-found' | 'succeeded' | 'failed' | 'rejected' | 'uncertain'
  outcome_code text,                       -- ReadErrorCode, ActionErrorCode or a domain failure code
  definition_id text,                      -- result object definition, or the action definition
  target_type text,                        -- requested get target, retained even when absent
  target_key text,
  invocation_id text,                      -- invocation executed or replayed
  replayed boolean NOT NULL DEFAULT false,
  details jsonb NOT NULL DEFAULT '{}',     -- kind-specific: traversalId, from, hasMore, truncated, refresh
  PRIMARY KEY (graph_id, id)
);
CREATE INDEX ON relate.operations (graph_id, recorded_at, id);
CREATE INDEX ON relate.operations (graph_id, parent_operation_id) WHERE parent_operation_id IS NOT NULL;
CREATE INDEX ON relate.operations (graph_id, actor_kind, actor_id, recorded_at);
CREATE INDEX ON relate.operations (graph_id, request_id);
CREATE INDEX ON relate.operations (graph_id, invocation_id) WHERE invocation_id IS NOT NULL;

-- What an operation touched: the lineage edges.
CREATE TABLE relate.operation_objects (
  graph_id text NOT NULL,
  operation_id uuid NOT NULL,
  ordinal integer NOT NULL,                -- position in the typed result
  object_type text NOT NULL,
  object_key text NOT NULL,
  role text NOT NULL,                      -- 'target' | 'returned' | 'traversal-origin'
  returned text[] NOT NULL DEFAULT '{}',   -- stable property definition IDs
  forbidden text[] NOT NULL DEFAULT '{}',
  unavailable text[] NOT NULL DEFAULT '{}',
  PRIMARY KEY (graph_id, operation_id, object_type, object_key, role),
  FOREIGN KEY (graph_id, operation_id)
    REFERENCES relate.operations(graph_id, id) ON DELETE CASCADE
);
CREATE INDEX ON relate.operation_objects (graph_id, object_type, object_key, operation_id);

-- One row per committed change to one object.
CREATE TABLE relate.changes (
  graph_id text NOT NULL REFERENCES relate.graphs(graph_id),
  id uuid NOT NULL,                        -- UUIDv7 identity, NOT the feed cursor
  schema_version smallint NOT NULL,
  position bigint NOT NULL,                -- publication order from feed_streams
  kind text NOT NULL,                      -- 'created' | 'adopted' | 'updated' | 'deleted' | 'restored'
  origin text NOT NULL,                    -- 'native' | 'adoption' | 'source-refresh'
  object_type text NOT NULL,
  object_key text NOT NULL,
  changed_property_ids text[] NOT NULL,
  operation_id uuid NOT NULL,              -- the attempt that committed it; may have no operations row
  parent_operation_id uuid,                -- e.g. the read that triggered the refresh
  invocation_id text,                      -- native changes only; source changes link through operation IDs
  actor_kind text NOT NULL,
  actor_id text NOT NULL,
  triggered_by_kind text,                  -- required for source-refresh: 'principal' | 'system'
  triggered_by_id text,                    -- trusted trigger snapshot, independent of operation retention
  context jsonb NOT NULL,                  -- OperationContext snapshot
  definition_revision text NOT NULL,
  occurred_at timestamptz NOT NULL,
  recorded_at timestamptz NOT NULL,
  details jsonb NOT NULL DEFAULT '{}',     -- sourceDefinitionId for source-origin changes
  PRIMARY KEY (graph_id, id),
  UNIQUE (graph_id, position)
);
CREATE INDEX ON relate.changes (graph_id, object_type, object_key, position);
CREATE INDEX ON relate.changes (graph_id, actor_kind, actor_id, position);
CREATE INDEX ON relate.changes (graph_id, invocation_id) WHERE invocation_id IS NOT NULL;

-- One row per invocation that reached a durable receipt, succeeded or failed.
CREATE TABLE relate.invocation_events (
  graph_id text NOT NULL REFERENCES relate.graphs(graph_id),
  id uuid NOT NULL,
  schema_version smallint NOT NULL,
  position bigint NOT NULL,                -- shares feed_streams with changes
  kind text NOT NULL,                      -- 'invocation-succeeded' | 'invocation-failed'
  action_id text NOT NULL,
  invocation_id text NOT NULL,
  failure_code text,                       -- domain failure code for 'invocation-failed'
  operation_id uuid NOT NULL,
  actor_kind text NOT NULL,
  actor_id text NOT NULL,
  context jsonb NOT NULL,
  definition_revision text NOT NULL,
  occurred_at timestamptz NOT NULL,
  recorded_at timestamptz NOT NULL,
  PRIMARY KEY (graph_id, id),
  UNIQUE (graph_id, position),
  UNIQUE (graph_id, invocation_id)
);
CREATE INDEX ON relate.invocation_events (graph_id, action_id, position);
CREATE INDEX ON relate.invocation_events (graph_id, actor_kind, actor_id, position);

-- One transactional counter and retention floor per graph, shared by changes
-- and invocation events.
CREATE TABLE relate.feed_streams (
  graph_id text PRIMARY KEY REFERENCES relate.graphs(graph_id),
  stream_id text NOT NULL,                 -- new identity only on explicit reset
  position bigint NOT NULL DEFAULT 0,      -- last committed
  floor bigint NOT NULL DEFAULT 0          -- positions at or below are pruned
);

ALTER TABLE relate.native_invocations RENAME TO invocations;
ALTER TABLE relate.invocations
  ADD COLUMN operation_id uuid,
  ADD COLUMN request_id text,
  ADD COLUMN transport text,
  ADD COLUMN definition_revision text,
  ADD COLUMN started_at timestamptz,
  ADD COLUMN completed_at timestamptz;

ALTER TABLE relate.value_changes RENAME TO object_versions;
ALTER TABLE relate.object_versions ADD COLUMN change_id uuid;

-- Creation and adoption provenance, kept for the object's lifetime.
ALTER TABLE relate.native_objects
  ADD COLUMN created_by_kind text,
  ADD COLUMN created_by_id text,
  ADD COLUMN created_invocation_id text,
  ADD COLUMN created_operation_id uuid;
ALTER TABLE relate.objects
  ADD COLUMN adopted_by_kind text,
  ADD COLUMN adopted_by_id text,
  ADD COLUMN adopted_at timestamptz,
  ADD COLUMN adopted_operation_id uuid;
```

`feed_streams` stays a separate row rather than columns on `graphs`: both source
acceptance (`packages/postgres/src/index.ts`) and native transactions
(`packages/postgres/src/native.ts`) hold `FOR SHARE` on the graphs row for the
whole transaction, and two holders upgrading to `FOR UPDATE` at commit time
would deadlock.

Memory stores keep the same two families and object provenance with the same
semantics and bounded feed and operation retention; memory need not gain object
versions solely for activity.

### Why columns, not one JSON union

A new kind of change is a new `kind` value with the same columns: native update
and delete when they exist, merges and migrations from the history design,
future user-authored domain events. The invariants a feed relies on, one
position, one object, one cause, hold for every future kind without an extra
object index table. A new kind of operation (a sync run, a migration run, a
write-back to a source) is likewise a new `kind` with actor, context, timing and
outcome already in place. `details` is the extension slot for kind-specific
metadata; the typed columns are the truth, so there is no duplicated JSON to
validate against them.

## Record contract

Transport-safe types belong to `@relate/protocol`. Schema versions are
independent of graph definition revisions. Additive optional fields may retain a
version; incompatible semantics require a new version. Consumers must be able to
skip unsupported kinds/versions while advancing their feed checkpoint.

```ts
export type ActivityActor =
  | { readonly kind: 'principal'; readonly id: string }
  | { readonly kind: 'system'; readonly id: string }
  /** A source system observed to have changed; id is the source definition ID. */
  | { readonly kind: 'source'; readonly id: string };

export interface OperationContext {
  readonly requestId: string;
  readonly transport: 'embedded' | 'http' | 'mcp';
  readonly executionId?: string;
  readonly runtimeId?: string;
  /** Supplied only by trusted host attribution, never an authorization grant. */
  readonly initiator?: ActivityActor;
}

export interface ActivityObjectRef {
  readonly objectDefinitionId: string;
  readonly objectId: string;
}

export interface OperationObject extends ActivityObjectRef {
  readonly role: 'target' | 'returned' | 'traversal-origin';
  readonly returned: readonly string[]; // Stable property definition IDs.
  readonly forbidden: readonly string[];
  readonly unavailable: readonly string[];
}

export type OperationOutcome =
  | { readonly status: 'ok' | 'not-found' }
  | { readonly status: 'succeeded' }
  | { readonly status: 'failed'; readonly code: string } // domain failure
  | {
      readonly status: 'rejected';
      readonly code: ReadErrorCode | Exclude<ActionErrorCode, 'uncertain'>;
    }
  | { readonly status: 'uncertain' };

export interface Operation {

  readonly parentOperationId?: string; // Set for nested work such as a read-triggered refresh.
  readonly graphId: string;

  readonly completedAt: string;
  readonly durationMs: number;
  readonly recordedAt: string;

    readonly traversalId?: string;
```

Rules that keep these records honest:

- The runtime assigns the authenticated principal as actor; trusted host
  operations use an explicitly supplied host actor or a named system actor.
  `initiator` can identify a person for whom an agent acts, but does not change
  the principal used for permission checks. A source-refresh change has the
  source as actor and snapshots the triggering principal or system actor in
  `triggeredBy`. Its refresh operation uses that triggering actor too.
  `parentOperationId` is an optional join to the enclosing attempt, whose row
  may be absent. Trigger attribution survives without either operation row; it
  never establishes provider authorship. `initiator` retains its separate
  acting-on-behalf-of meaning and is not substituted for `triggeredBy`.
- `operationId` identifies one attempt and differs on every retry.
  `ActionContext.idempotencyId` is stable across retries and is what handlers
  forward to external systems. Neither may be substituted for the other.
- `created` means Relate created the object (origin `native`). The first
  acceptance of an existing source record is `adopted` (origin `adoption`), so a
  notification consumer can tell new objects from imports.
- Work an operation triggers that has its own outcome, currently a
  read-triggered refresh, is a nested operation with `parentOperationId`.
  Changes it commits carry both IDs. This version adds no standalone
  `host.refresh` API. An explicit consumer read with `{ refresh: true }` still
  records a read and, when source fetching is attempted, a nested refresh.
- An operation's `objects` list is derived from its typed result, never supplied
  by a consumer. It includes requested targets, returned records and traversal
  origins. A failed get retains its requested identity without asserting the
  object exists; hidden and missing objects have the same `not-found` outcome.
  Query predicates and action inputs are never mined for IDs.
- `objects` with role `returned` contains only the final page's delivered
  objects, in result order, captured after selection, authorization and
  completeness checks but before compact evidence presentation discards detail.
  Internal reads during actions or query evaluation are not separate consumer
  operations. Action authorization dependencies remain receipt storage evidence.
- Operations are recorded once they settle, only through the best-effort queue.
  A feed entry describes the moment of the change inside its transaction, not
  the enclosing request's start. Store order is distinct from these wall-clock
  timestamps. Source-origin changes report when Relate observed a change; they
  do not establish the provider's change time or author.
- A `created` or `adopted` change lists every property the object has; an
  `updated` change lists the mapped properties whose values changed; `deleted`
  and `restored` list none. A raw provider field change alone does not produce
  an `updated` change.

## Context and causal links

```ts
// Node binding: a transport binds a trusted principal per request.
operations(principal: Principal, context?: Partial<OperationContext>): ConsumerOperations;
const ops = runtime.operations(principal, { requestId, transport: 'http' });

// Embedded callers get a fresh default request ID for EACH operation.
const alice = runtime.as(alicePrincipal);
await alice.objects.Customer.get('cus_01'); // requestId req_1, operation op_1
await alice.objects.Customer.get('cus_02'); // requestId req_2, operation op_2
```

Missing context defaults to embedded transport and a fresh request ID per call,
not per long-lived binding. Each operation also gets its own `id`. Internal work
carries that operation's context; feed entries it commits reference its ID, and
nested operations reference it as their parent. Transports assign and forward
the operation ID when they need to own a pre-dispatch rejection. Context is
snapshotted and cannot override actor or definition revision. The engine accepts
it on reads, queries, traversals, invocations, receipt lookup and adoption.

An invocation's native changes and its invocation event share its stable
`invocationId`. Independently committed source-refresh changes and refresh
operations do not inherit it, including during replay and receipt lookup. They
use operation and parent-operation IDs, since the enclosing attempt may never
produce a receipt. An invocation filter therefore does not include those source
changes. A replay is a new operation that refers to the original invocation and
commits no native effect, change or invocation event of its own. Neither request
IDs nor invocation IDs are identity or ordering keys.

## Recording changes

### Native transactions

Extend the native transaction capability with atomic change append:

```ts
// Inside the existing native transaction, after final authorization checks.
await transaction.saveInvocation(invocation);
await transaction.appendChanges([createdReview]); // drafts: kind, object, properties
await transaction.appendInvocationEvent(succeeded); // kind, action, invocation
```

After a fresh idempotency claim, allocate the invocation ID before running the
handler or inserting objects. Reuse it for native creation provenance, the
terminal receipt and the invocation event. A replay keeps the saved receipt's
ID. Allocation alone creates no durable invocation; a rejected or rolled-back
attempt leaves no invocation record or native provenance behind.

Native object creation stores creation provenance (actor, invocation, operation)
on the object row in the same write. Drafts carry what the runtime knows: kind,
origin, object, changed property IDs, operation, invocation, actor, context and
occurrence time. The runtime assigns stable IDs; the adapter supplies
`recordedAt` and positions. `appendChanges` stages drafts within the
transaction; it participates in transaction/savepoint rollback and handle
revocation. The adapter publishes staged drafts after the transaction callback
succeeds and before COMMIT, so no user callback runs while holding the
publication lock. It is not an independent store call or an after-commit
callback. The operation row is not part of the transaction: the runtime enqueues
it once the outcome is known.

- Success commits the objects with their creation provenance, the invocation,
  one `created` change per committed creation and one `invocation-succeeded`
  event.
- A domain failure rolls back effects and commits only the failed receipt and
  its `invocation-failed` event; no changes.
- A rejection before receipt creation (denied, invalid input, conflict,
  deadline) commits no native effect, invocation or invocation event. Its
  operation row records `rejected` with no `invocationId`.
- Known rollback commits no native effect, invocation, change or invocation
  event.
- Replay commits no native effect, invocation, change or invocation event. Its
  operation row records `replayed: true` and the original `invocationId`.
- In every case above, receipt authorization reads the action's dependencies and
  may refresh sources. Those refreshes are nested operations of the attempt and
  commit their own changes independently, whether or not the action commits.
  Their changes snapshot `triggeredBy` and omit `invocationId`.
- A lost COMMIT acknowledgement makes the operation row record `uncertain`. If
  the commit succeeded, its feed entries already exist and are authoritative.
  Never turn uncertainty into a known rejection or automatically execute the
  action again.

This describes Relate-owned state. External effects performed by an action are
not made transactional by a feed entry.

### Source acceptance

Extend `ObservationStore.accept` with trusted provenance (actor, `triggeredBy`
for source refreshes, operation/context, parent operation, occurrence time and a
preassigned candidate change ID). Under its existing acceptance lock, the
adapter determines the actual winning transition and writes the observation, any
version row and the change together. A first membership acceptance also writes
adoption provenance on the object row. The runtime owns the semantics; the
adapter does not fetch sources or evaluate authorization.

| Accepted transition                        | Change kind, origin          | Change actor               | Version row (Postgres)                       |
| ------------------------------------------ | ---------------------------- | -------------------------- | -------------------------------------------- |
| First membership acceptance                | `adopted`, `adoption`        | adopting principal or host | `origin = adoption`                          |
| Mapped values changed, state still present | `updated`, `source-refresh`  | source                     | `origin = source-refresh`                    |
| Present to deleted                         | `deleted`, `source-refresh`  | source                     | `origin = source-refresh`, `state = deleted` |
| Deleted to present                         | `restored`, `source-refresh` | source                     | `origin = source-refresh`                    |
| Unchanged, superseded, replay              | none                         |                            | none                                         |

Concurrent adoption/refresh uses the winning accepted state, not a diff computed
outside the transaction. A repeated acceptance does not duplicate the change.
The version reference names the row actually written, when one exists; an absent
reference means no exact historical payload is available through that change.
Memory and Postgres must agree on change semantics.

If required change persistence fails, observation acceptance fails atomically
using the existing retention failure/uncertainty contract. Whether the enclosing
read can return freshly fetched data is still governed by its existing evidence
and retention semantics; activity must not silently claim confirmed retention.

### Refresh operation outcomes

A nested refresh starts when the runtime attempts source resolution for a stale
or explicitly refreshed observation. A fresh observation that needs no fetch
produces no refresh operation. The refresh's outcome is separate from the
enclosing read's outcome: a read may return available data after a failed fetch
or retention attempt under the existing read contract.

| Refresh result                                                                                       | Operation outcome                                      | `details.refresh` | Feed effect from this attempt     |
| ---------------------------------------------------------------------------------------------------- | ------------------------------------------------------ | ----------------- | --------------------------------- |
| Confirmed acceptance changed mapped values or present/deleted state                                  | `ok`                                                   | `changed`         | One change                        |
| Confirmed acceptance changed no mapped values or state, including raw-only changes                   | `ok`                                                   | `unchanged`       | None                              |
| A competing observation won; this attempt was superseded or replayed an already accepted observation | `ok`                                                   | `superseded`      | No new change                     |
| Provider unavailable or timed out                                                                    | `rejected`, code `unavailable`                         | Absent            | None                              |
| Provider access denied                                                                               | `rejected`, code `denied`                              | Absent            | None                              |
| Invalid observation or conflicting ordering evidence                                                 | `rejected`, code `invalid`                             | Absent            | None                              |
| Acceptance failed with known rollback                                                                | `rejected`, sanitized `unavailable` or `internal` code | Absent            | None                              |
| Acceptance commit remains unconfirmed                                                                | `uncertain`                                            | Absent            | A change may already be committed |

`changed` describes this attempt's confirmed accepted business-state transition,
not a successful fetch or a raw provider difference. The adapter returns the
transition classification from the same locked comparison that decides whether
to append a change. Do not derive it from a diff outside that transaction or
directly from `Acceptance = 'changed'`, which also covers raw-only differences.
Readback may resolve an uncertain acceptance only when it identifies this
attempt's outcome; seeing the same current values alone is insufficient.

Every attempted refresh is eligible for a best-effort operation row, including
unchanged, superseded and failed refreshes. Only accepted business-state changes
produce feed entries. The enclosing read's field evidence and access decisions
retain their existing semantics.

### Publication order

For the first Postgres implementation, allocate positions from the
`feed_streams` row, holding its lock until commit. Allocate the batch and insert
its changes and invocation event together as the final database work, after
domain validation and without provider I/O or user callbacks under the lock.
Every feed writer follows this protocol and consistent lock ordering. Memory
implements the equivalent atomic append. Operations never take this lock.

This ensures that no earlier position can become visible after a later committed
position has been returned. A rolled-back transaction exposes neither its feed
entries nor its counter update. Do not replace this with UUID ordering or a bare
SQL sequence: allocation order alone does not establish commit visibility order.
The lock serializes a short final section per graph, which is an explicit
throughput tradeoff to measure before considering a different publisher.

The retained feed also supplies outgoing delivery; no separate outbox or broker
is required for this first implementation. A future exporter stores its own
checkpoints/delivery state outside feed rows.

## Recording operations

Every operation, including one that committed feed entries, is recorded through
one bounded queue per runtime, with limits on entries and bytes and a single
writer. The writer may append a bounded batch; only one append is in flight per
runtime. This first implementation makes no automatic append retries and adds no
durable queue or started/finished operation lifecycle. It never awaits delivery
on the consumer result path. The runtime isolates synchronous store throws and
rejected promises. It does not claim literally zero latency or resource
overhead.

Provide capture configuration, drop counters and a host error hook. Queue
overflow, write failure and shutdown abandonment are observable without trying
to report them only through the failing store. Diagnostics use sanitized failure
codes and operation kinds, not raw exception messages, IDs or values. Callback
failures must not affect operations.

A hung append occupies the single writer; do not start replacement writes while
it is still in flight. Store implementations must support bounded I/O or
cancellation that releases resources. Best-effort traffic must not exhaust the
pool required by committed writes. On a failed append, report the dropped batch
and continue with later queued rows. Even without runtime retries, the store's
append contract deduplicates identical IDs/payloads and rejects conflicting
reuse. Future retries would have to reuse operation IDs.

Bound individual rows as well as buffers: an operation whose `objects` list
exceeds the configured limit is recorded with
`details.truncated = { omittedObjects }` and counted, rather than silently
claiming a complete lineage. Stores preserve `objects` order (`ordinal` in
Postgres).

`close()` first drains tracked operations, then drains capture with an explicit
flush deadline. The existing Node close implementation has no such deadline;
adding it is implementation work. Deadline expiry reports abandoned capture and
must not close a host-owned shared store. Default queue sizes and flush duration
are implementation choices, exposed and tested.

## Host reading contract

Filters, pages and errors are transport-safe protocol types. Storage interfaces
in `relate` consume them, so future HTTP clients need not depend on runtime
code.

```ts
interface ActivityFilter {
  readonly actor?: ActivityActor;
  readonly objectDefinitionId?: string;
  readonly object?: ActivityObjectRef;
  readonly invocationId?: string;
  readonly operationId?: string;
  readonly requestId?: string;
  readonly from?: string; // Inclusive occurredAt/startedAt, RFC 3339.
  readonly to?: string;
}

interface ChangeFilter extends ActivityFilter {
  readonly kinds?: readonly Change['kind'][];
  readonly origins?: readonly Change['origin'][];
}

interface FeedFilter extends ActivityFilter {
  readonly kinds?: readonly FeedEntry['kind'][];
  readonly origins?: readonly Change['origin'][]; // Changes only.
  readonly actionDefinitionId?: string; // Invocation events only.
}

interface OperationFilter extends ActivityFilter {
  readonly kinds?: readonly Operation['kind'][];
  readonly objectRole?: OperationObject['role']; // Requires object or objectDefinitionId.
  readonly outcomes?: readonly OperationOutcome['status'][];
}

interface Page<T> {
  readonly entries: readonly T[];
  readonly nextCursor: string;
  readonly hasMore: boolean;
}

type TimelineEntry =
  | { readonly family: 'feed'; readonly entry: FeedEntry }
  | { readonly family: 'operation'; readonly entry: Operation };

interface ActivityReader {
  status(): Promise<
    | { readonly state: 'unsupported' }
    | {
        readonly state: 'available';
        readonly durability: 'volatile' | 'persistent';
        readonly operationCapture: 'enabled' | 'disabled';
      }
  >;
  readonly feed: {
    /** Oldest publication first: changes and invocation events. */
    read(options?: {
      filter?: FeedFilter;
      cursor?: string;
      limit?: number;
    }): Promise<Page<FeedEntry>>;
  };
  readonly changes: {
    /** Newest publication first: browsing. */
    list(options?: {
      filter?: ChangeFilter;
      cursor?: string;
      limit?: number;
    }): Promise<Page<Change>>;
  };
  readonly operations: {
    /** Newest recorded first; best-effort rows, no feed semantics. */
    list(options?: {
      filter?: OperationFilter;
      cursor?: string;
      limit?: number;
    }): Promise<Page<Operation>>;
  };
  /** Both families by occurrence time, newest first. For the Inspector; no feed semantics. */
  timeline(options?: {
    filter?: ActivityFilter;
    cursor?: string;
    limit?: number;
  }): Promise<Page<TimelineEntry>>;
  /** Who created or adopted an object. Undefined when the object is unknown. */
  provenance(object: ActivityObjectRef): Promise<ObjectProvenance | undefined>;
}

// Store methods additionally take graphId; the host reader binds its graph.
interface ActivityStore {
  appendOperations(
    graphId: string,
    drafts: readonly OperationDraft[],
  ): Promise<void>;
  // status, feed.read, changes.list, operations.list, timeline, provenance: each also takes graphId
}
```

`OperationDraft` is an `Operation` without store-assigned recording time. Every
operation, including one that committed feed entries, enters through
`appendOperations`.

- `changes.list` returns newest publication first. Its first page pins the
  committed high-water position, so later pages are stable against new appends.
- `operations.list` returns newest first by `(recordedAt, id)`; `id` breaks
  ties. The first page pins that pair as an upper bound. Operation rows arrive
  asynchronously, so a row can become visible with a timestamp a page sequence
  has already passed. That sequence does not return it; restarting from the
  first page does. A late row below the current descending cursor can appear on
  a later page. The bound does not freeze the set of visible operation rows.
  This is browsing, not a feed.
- `timeline` merges feed entries and operations by occurrence time
  (`occurredAt`, or `startedAt` for operations), newest first, breaking ties by
  family (feed first) then ID. It pins the feed position and the operation bound
  separately, and has the same late-arrival behaviour for operations.
- `feed.read` returns oldest publication first, starting at the retention floor
  when no cursor is supplied. Thereafter it returns every matching retained
  entry after the checkpoint. A finite call reads to a captured committed
  high-water mark; consumers poll again to follow new appends.
- Cursors are opaque, validated and bound to graph, stream identity, method and
  normalized filter. Changed filters or a cursor from another graph/method
  reject as `invalid-cursor`. Limits default to 50 and range from 1 to 500. A
  resumed call inherits its cursor's filter when none is supplied.
- `nextCursor` describes the range scanned, including filtered-out rows. An
  empty filtered page can advance it. Never advance past unreturned matching
  rows; `hasMore` tells whether more matches remain in the call's range.
- Filters combine with AND; values within `kinds` or `outcomes` combine with OR.
  Reject contradictory object and object-definition filters. All references
  match within the bound graph. For operations, object-definition filtering
  matches lineage references and the result definition even for an empty page; a
  role filter requires a matching reference.
- Object filters match direct references only: a change's own object and an
  operation's lineage. A review created for a customer references the review,
  not the customer, so a customer filter does not return it. Invocation events
  match actor, invocation, operation, request and action-definition filters,
  never object filters.
- Actor filters match `actor`, not `triggeredBy` or `context.initiator`. For
  example, Fin's operation rows match Fin, while a source-refresh change matches
  its source actor. Trigger attribution is returned metadata, not an additional
  filter in this version.
- Re-reading a checkpoint may return duplicates; consumers deduplicate using
  entry identity and checkpoint only after successful processing. There is no
  exactly-once external side-effect guarantee.
- Unsupported activity rejects reads as `unsupported`, not an empty history.
  Store failures are `unavailable`, malformed options are `invalid-request`.
  Expired/lost stream positions are `cursor-expired`.

### Retention and restart

Memory retains the newest 10,000 feed entries and 10,000 operations per graph,
each with a byte bound as well. Feed eviction removes a contiguous publication
prefix and advances the retention floor; operation eviction removes the oldest
recorded rows. A new memory store has a new stream identity; its old cursors
expire. Oversized committed feed batches reject the associated transaction.
Object provenance lives on object rows and is never evicted with the feed.

Postgres retains both families; there is no pruning yet. The floor and
expired-cursor contract is specified now so pruning can be added later without
changing cursors. Future feed pruning removes a contiguous prefix and advances
the floor atomically; it never resets/reuses positions or changes stream
identity on an ordinary restart. Future operation pruning removes rows older
than a given time together with their lineage rows. Neither removes object
provenance. A feed cursor behind the floor fails explicitly; it must not
silently skip deleted entries. Consumers then rebuild their own projection or
explicitly choose to resume from retained history. Version rows can expire
independently; resolving a missing version reference must report that absence.

Read each page, its high-water mark and its retention floor from one consistent
snapshot so concurrent pruning cannot create an undetected gap. Operation append
deduplication is guaranteed while the row is retained. The runtime does not
retry in this version; any future retries must be bounded to that retention
window rather than resurrecting pruned history.

Automatic retention schedules and subject-specific erasure require separate
policy design. Append-only describes normal recording, not a promise that data
can never be removed. Prune authorization/options are future API work; the
retention-floor and expired-cursor contract is required now.

## Third-party applications and data access

Only trusted host code and the Inspector can read activity initially:
`runtime.host.activity` implements `ActivityReader`. No activity methods are
added to `as(user)`, `ConsumerOperations`, MCP tools or consumer HTTP routes.

Change metadata supports notifications, timelines, cache invalidation and
triggering an authorized refresh. Fetching an object after a change returns its
current state, not necessarily its change-time state. Exact historical
applications need a retained version reference and a separately authorized
history API. A reference or change never grants permission to its payload.

Before remote exposure, define integration credentials, graph/kind scopes and
field projections. Current permission to read an object does not automatically
authorize its access history. Per-user feeds need explicit historical visibility
rules. Do not export trusted raw rows indiscriminately.

A later export adapter maps changes to CloudEvents: a stable installation/graph
URI becomes `source`, change ID becomes `id`, `relate.object.<kind>` becomes
`type` (`relate.invocation.<succeeded|failed>` for invocation events),
`occurredAt` becomes `time`, and the versioned selected metadata becomes `data`.
Installation identity must distinguish independent deployments that use the same
graph ID. Preserve source/ID across retries. CloudEvents supplies an
interoperable envelope, not persistence, ordering or delivery guarantees.

Primary references verified on 2026-10-13:

- [CloudEvents 1.0.2](https://github.com/cloudevents/spec/blob/v1.0.2/cloudevents/spec.md):
  envelope and source/ID duplicate identity; optional boundary mapping, not a
  runtime dependency.
- [PostgreSQL sequence semantics](https://www.postgresql.org/docs/18/functions-sequence.html):
  sequence allocation is independent of transaction rollback; it is not the
  publication protocol.

## `relate dev` and the Inspector

1. The dev server passes context and operation identity through IPC to the
   runtime host. The runtime captures operations and committed changes.
2. After committed publication, the runtime host forwards rows to the dev
   server: `{ type: 'activity', runtimeId, feed, operations }`. Forwarding is
   best effort and never part of the native/source transaction. A feed reader
   can recover committed entries if immediate forwarding misses an
   acknowledgement.
3. The dev server deduplicates by graph/row ID and retains a bounded display
   history across runtime-host restarts. It is a development projection, not a
   durable integration checkpoint or a replacement for the store's feed.
4. L1 calls and L2 agent executions remain dev-server events and join by request
   and execution IDs. The Inspector renders operations and changes in place of
   L3, distinguishing committed feed entries, attempts, nested refreshes and
   uncertain outcomes.
5. Delete `packages/cli/src/dev/activity/operations.ts` when runtime capture is
   connected. Keep only explicit pre-dispatch rejection capture at the routing
   boundary. Development progress/running indicators can remain transient UI
   state; they do not mutate immutable persisted rows.

Losing a memory runtime can still lose unforwarded volatile rows. Retaining a
dev-server display across saves is not a durability guarantee.

## Acceptance tests

- Creation with its provenance, receipt, change and `invocation-succeeded` event
  commit together; injected feed-write failure rolls them all back. A failed
  domain action records its receipt and `invocation-failed` event but no
  rolled-back creations. Dropping the operation row loses no feed entry or
  provenance. Savepoint and revoked-handle behaviour is preserved.
- A rejected action records no invocation event and an operation row without
  `invocationId`. An action whose receipt authorization refreshes a source keeps
  that refresh's committed change even when the action is rejected or rolls
  back; the refresh is a nested operation of the attempt. Its operation and
  change omit `invocationId`, even on a successful invocation or receipt replay;
  parent IDs retain the causal link. Native creation provenance, receipt and
  invocation event share the ID allocated before the handler ran.
- A crash after COMMIT but before response/forwarding leaves feed entries
  recoverable from Postgres after restart. Lost acknowledgements produce
  `uncertain` operation rows while committed feed entries remain authoritative.
- Concurrent idempotent invocations execute once; replay adds no native change
  or invocation event and records at most one `replayed` operation per attempt.
  Replay authorization may still commit independent source-refresh changes.
  Repeated store appends deduplicate identical IDs and reject conflicting reuse;
  the runtime does not automatically retry a failed append.
- Retries of one request get distinct operation IDs and the same handler
  `idempotencyId`. Keep the existing
  `reuses the idempotency ID after rollback and runtime reconstruction` test in
  `tests/support/native-action-contract.ts`.
- Native creation produces a `created` change with origin `native` and creation
  provenance on the object. Source adoption produces one `adopted` change (never
  `created`) and adoption provenance; value changes `updated`; tombstones
  `deleted`; resurrection `restored`. Source-refresh changes have the source as
  actor.
- A read that refreshes records a nested `refresh` operation that names its
  parent and whether the record changed; a read of a fresh observation records
  none. Concurrent refresh losers and unchanged/raw-only observations emit no
  feed entry but still enqueue their operation rows with `superseded` or
  `unchanged` as appropriate. Provider denial, unavailable/invalid fetches,
  known retention failure and unresolved commit uncertainty follow the refresh
  outcome table, independently of the enclosing read's outcome. Version
  references identify the actual accepted row. Memory/Postgres semantics agree
  without requiring memory version storage.
- Reads capture stable property IDs and distinguish forbidden/unavailable;
  compact/full evidence modes produce equivalent lineage. Lineage keeps result
  order through a Postgres round trip; oversized lineage records
  `details.truncated`. Hidden and missing gets retain the same requested target
  and indistinguishable outcomes.
- Query/internal reads do not over-report delivered objects. Traversal origins
  retain their own object-definition identity. No values, inputs or raw errors
  appear in any row or capture diagnostic.
- Operation write rejection, synchronous throw, hanging I/O and queue overflow
  do not change consumer results; resource bounds and drop diagnostics hold.
  There is at most one in-flight append per runtime and no automatic retry;
  failed batches do not block later rows once their resources are released.
  Operation capture never acquires the feed publication lock. Shutdown drains
  operations before bounded flushing. Disabling capture leaves required feed
  writes and object provenance enabled.
- Many calls through one embedded binding get distinct default request and
  operation IDs. Transport-bound calls share request context but have distinct
  operation IDs. Retired routing records exactly one pre-dispatch operation.
- Delay an earlier change writer while a later writer runs: advancing a feed
  checkpoint cannot skip a change that commits afterwards behind it. Run this
  with multiple Postgres connections, rollback, mixed source/native writers and
  restart.
- Catch-up larger than one page returns all matches in order, changes and
  invocation events interleaved by position. Empty filtered scans advance
  safely; cursor graph/filter/method binding rejects misuse. New feed writes do
  not disturb pinned descending change pages. A late operation row whose
  ordering position has already been passed is absent from subsequent pages and
  visible after browsing restarts. A late row below the current descending
  cursor can appear on a later page. Test both cases for operation browsing and
  the combined timeline; equal timestamps use the documented tie-breakers.
- A customer filter returns changes to that customer and operations whose
  lineage references it, but not a review created for it.
- Memory eviction of operations leaves every feed entry readable with its own
  actor and context. A source-refresh change also retains `triggeredBy` when
  both its operation and parent rows are dropped, evicted or capture is
  disabled. Actor filtering still matches the source. Feed eviction expires
  affected cursors explicitly, as does stream replacement. Object provenance
  survives eviction of every feed entry. The same holds for Postgres pruning
  when it is added. Persistent restart preserves valid cursors and IDs.
  Unsupported, unavailable and genuinely empty activity remain distinguishable.
- Legacy `invocations`, `object_versions`, `objects` and `native_objects` rows
  keep their keys and evidence with null provenance (`kind: 'unknown'`); nothing
  invents an operation, change or invocation event for them.
- A store that advertises `activity` without the atomic hooks for every write
  capability it exposes is rejected at runtime setup.
- No consumer surface exposes trusted history. Inspector joins runtime rows with
  L1/L2, deduplicates forwarded rows and preserves its bounded display history
  across runtime-host restarts.

## Open questions

- **Object identity tables.** `objects` holds source-backed identity and the
  latest observation; `native_objects` holds Relate-owned values. The minimum
  coherence step is renaming `objects` to `source_objects`. The fuller step,
  which "one object enriched from several sources" needs anyway, is one
  `objects` identity table plus per-connection source aliases and observations;
  it would also let `object_versions` keep a real foreign key once native rows
  join it. Neither is part of this spec. This spec adds creation and adoption
  provenance columns to both tables; the later split must move them onto the
  identity table.
- **Related-object references.** v1 filters match direct references only. If a
  customer timeline should show reviews created for that customer, define
  explicit related-object references on changes; never mine action inputs.
- **Consumer access to provenance.** `provenance` is host-only, like the rest of
  activity. Showing "created by" to `as(user)` callers needs its own
  authorization rule.
- **Sync runs.** A sync worker run will be another operation kind, and its
  refreshes will be nested operations under it.

## Deferred work

- Remote admin/integration authorization and per-user historical visibility.
- HTTP/SSE/webhook delivery, CloudEvents adapter and managed exporter
  checkpoints.
- A standalone `host.refresh` API. Consumer reads with `{ refresh: true }`
  already participate in nested refresh capture; host-triggered refreshes need a
  separate public contract before they are added.
- Exact historical-value retrieval APIs and their authorization/retention
  policy.
- Automatic retention schedules, subject-specific erasure and archival storage.
- Native update/delete changes when those operations exist; they use the same
  `updated`/`deleted` kinds and the same atomic recording contract.
- Additional operation kinds (sync runs, migrations, write-back), user-authored
  domain events as a change kind, and strict durable access auditing.
