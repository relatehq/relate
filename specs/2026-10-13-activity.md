# 2026-10-13: Runtime activity backbone

**Status:** design agreed and revised on 2026-10-13; not implemented. This
revision replaces the initial best-effort-only log design. It also replaces the
interim dev-server operation layer ("L3") described in
[2026-10-07: Inspector architecture and design record](./2026-10-07-inspector.md#activity-observation).

## Outcome

One shared account of activity in a Relate graph, usable by the Inspector,
trusted host applications and, later, authorized third-party integrations.
Activity answers both "what did someone attempt?" and "what actually changed?"
without making downstream applications reconstruct a timeline from domain
tables.

```ts
// Browse the activity involving one typed object, newest publication first.
const page = await runtime.host.activity.list({
  filter: {
    object: { objectDefinitionId: 'obj_customer', objectId: 'cus_123' },
  },
  limit: 50,
});

// Consume retained events in publication order, resuming after a checkpoint.
const batch = await runtime.host.activity.read({ cursor, limit: 100 });
for (const entry of batch.entries) await processIdempotently(entry);
await saveCheckpoint(batch.nextCursor);
```

These are proposed APIs. Activity contains metadata and typed references, never
property values, filter values, action inputs/outputs, agent code or raw errors.
Receipts, source history and object state retain their own responsibilities.
Activity is not an event-sourced replacement for those records.

## What exists today

| Concern                                 | Current owner                          | Change proposed here                                                                          |
| --------------------------------------- | -------------------------------------- | --------------------------------------------------------------------------------------------- |
| Native object state                     | `relate.native_objects`                | Retain state; link creation to its originating invocation                                     |
| Action replay and receipt authorization | `relate.native_invocations`            | Retain input, receipt and authorization evidence; add time, revision and operation provenance |
| Source identity and latest observation  | `relate.objects`                       | Retain current responsibility                                                                 |
| Observed source value history           | `relate.value_changes` (Postgres only) | Link each new history row to its corresponding activity event                                 |
| Read and request activity               | Dev-server L1–3 log, in memory         | Replace L3 graph observation with shared runtime entries                                      |

Native objects and receipts already commit together. Postgres already writes
value history in the transaction that accepts an observation. The new activity
contract extends those atomic boundaries. Existing records do not acquire
invented actors, timestamps or historical events during migration.

## Guarantees and ownership

| Event family                                                    | Capture guarantee when activity is supported                    |
| --------------------------------------------------------------- | --------------------------------------------------------------- |
| Native object created                                           | Atomic with the object and its invocation receipt               |
| New terminal invocation receipt, succeeded or domain-failed     | Atomic with the receipt                                         |
| Source object adopted or accepted business values/state changed | Atomic with accepted observation and any retained value history |
| Read, receipt lookup, invocation attempt/replay/rejection       | Best effort, bounded, with observable drops                     |

"Atomic" means the state change and its event both commit or both roll back.
Persistence survives normal process restart only with a persistent store; memory
provides the same atomicity but remains volatile. None of this promises infinite
retention or complete access auditing.

Failure to persist a required change event prevents its associated write from
committing. External delivery is asynchronous: a destination outage never
participates in a domain transaction. Reading existing objects and authorizing
receipts do not depend on reading activity.

The runtime defines event semantics and captures authorization-aware results.
Adapters implement atomic recording and publication ordering. A transport may
record an attempt it definitively rejected before dispatch, such as
`runtime-retired`; it never fabricates engine results or committed changes.
Unknown dispatch outcomes are not described as known rejection. There is one
owner for each attempt event, so transport and engine do not double-record it.

## Event contract

Transport-safe types belong to `@relate/protocol`. Event schema versions are
independent of graph definition revisions. Additive optional fields may retain a
version; incompatible semantics require a new version. Consumers must be able to
skip unsupported event types/versions while advancing their feed checkpoint.

```ts
export type ActivityActor =
  | { readonly kind: 'principal'; readonly id: string }
  | { readonly kind: 'system'; readonly id: string };

export interface OperationContext {
  readonly requestId: string;
  readonly transport: 'embedded' | 'http' | 'mcp';
  readonly executionId?: string;
  readonly runtimeId?: string;
  /** Supplied only by trusted host attribution, never an authorization grant. */
  readonly initiator?: ActivityActor;
}

export interface ActivityObjectRef {
  readonly objectDefinitionId: string;
  readonly objectId: string;
}

interface EntryBase {
  readonly id: string; // UUIDv7 identity, NOT a feed cursor.
  readonly schemaVersion: 1;
  readonly graphId: string;
  readonly definitionRevision: string;
  readonly occurredAt: string; // RFC 3339: runtime occurrence/observation time.
  readonly recordedAt: string; // RFC 3339: store recording time, not commit time.
  readonly actor: ActivityActor;
  readonly operationId: string; // One engine or pre-dispatch operation attempt.
  readonly context: OperationContext;
  readonly invocationId?: string;
  readonly causedByEventId?: string;
  readonly objects: readonly (ActivityObjectRef & {
    readonly role: 'target' | 'returned' | 'created' | 'traversal-origin';
  })[];
}

interface OperationTiming {
  readonly startedAt: string;
  readonly completedAt: string;
  readonly durationMs: number; // Measured with a monotonic clock.
}

type InvocationOutcome =
  | { readonly status: 'succeeded' }
  | { readonly status: 'failed'; readonly code: string };

export type ActivityEntry = EntryBase &
  (
    | {
        readonly type: 'read.completed';
        readonly timing: OperationTiming;
        readonly op: 'get' | 'query' | 'traverse';
        readonly objectDefinitionId: string; // Result object definition.
        readonly target?: ActivityObjectRef; // Requested get target, even if absent.
        readonly from?: ActivityObjectRef & { readonly traversalId: string };
        readonly results: readonly (ActivityObjectRef & {
          readonly returned: readonly string[]; // Stable property definition IDs.
          readonly forbidden: readonly string[];
          readonly unavailable: readonly string[];
        })[];
        readonly hasMore?: boolean;
        readonly outcome: 'ok' | 'not-found' | ReadErrorCode;
      }
    | {
        readonly type: 'invocation.attempted';
        readonly timing: OperationTiming;
        readonly actionDefinitionId: string;
        readonly replayed: boolean;
        readonly outcome:
          | InvocationOutcome
          | {
              readonly status: 'rejected';
              readonly code: Exclude<ActionErrorCode, 'uncertain'>;
            }
          | { readonly status: 'uncertain'; readonly code: 'uncertain' };
      }
    | {
        readonly type: 'invocation.recorded';
        readonly actionDefinitionId: string;
        readonly invocationId: string;
        readonly outcome: InvocationOutcome;
      }
    | {
        readonly type: 'receipt.read';
        readonly timing: OperationTiming;
        readonly actionDefinitionId: string;
        readonly invocationId: string;
        readonly outcome: 'ok' | ActionErrorCode;
      }
    | {
        readonly type: 'object.created';
        readonly object: ActivityObjectRef;
        readonly invocationId: string;
      }
    | {
        readonly type: 'object.adopted' | 'source.change-observed';
        readonly object: ActivityObjectRef;
        readonly sourceDefinitionId: string;
        readonly state: 'present' | 'deleted';
        readonly changedPropertyIds: readonly string[];
        /** Present only when the adapter retains the corresponding value history. */
        readonly history?: {
          readonly kind: 'source-change';
          readonly id: string;
        };
      }
  );
```

`ReadErrorCode` and `ActionErrorCode` above mean the public protocol error-code
unions. The runtime assigns the authenticated principal as actor; trusted host
operations use an explicitly supplied host actor or a named system actor.
`initiator` can identify a person for whom an agent acts, but does not change
the principal used for permission checks. Never infer provider authorship from
the principal whose read triggered a refresh.

Each event's `objects` index is derived from its typed payload, never supplied
independently by a consumer. It includes requested targets, returned records,
created records and traversal origins with their respective roles. References
always include the object definition ID. A failed get retains its requested
identity without asserting the object exists; hidden and missing objects still
have the same `not-found` outcome. Query predicates and action inputs are never
mined for arbitrary IDs to populate this index.

`results` contains only the final page's delivered objects, in result order.
Capture field statuses before compact evidence presentation discards detail, but
after selection, authorization and completeness checks determine the actual
result. Internal reads during actions or query evaluation must not masquerade as
separate consumer reads. Action authorization dependencies remain receipt
storage evidence.

Access events occur when the operation settles. Creation events describe the
creation, not the enclosing request's start. Store order is distinct from these
wall-clock timestamps. Source events report when Relate observed a change; they
do not establish the provider's change time or author.

## Context and causal links

```ts
// Node binding: a transport binds a trusted principal per request.
operations(principal: Principal, context?: Partial<OperationContext>): ConsumerOperations;
const ops = runtime.operations(principal, { requestId, transport: 'http' });

// Embedded callers get a fresh default request ID for EACH operation.
const alice = runtime.as(alicePrincipal);
await alice.objects.Customer.get('cus_123');
```

Missing context defaults to embedded transport and a fresh request ID per call,
not per long-lived binding. Each operation also gets its own `operationId`.
Internal work carries that operation's context; related events share its ID.
Transports assign and forward the operation ID when they need to own a
pre-dispatch rejection. Context is snapshotted and cannot override actor or
definition revision. The engine accepts it on reads, queries, traversals,
invocations, receipt lookup and adoption.

An invocation's committed events share its stable `invocationId`. A replay has a
new operation ID and refers to the original invocation. `causedByEventId` links
a later operation triggered by an earlier event where known. Neither request IDs
nor invocation IDs are event identity or ordering keys.

## Recording committed activity

### Native transactions

Extend the native transaction capability with atomic activity append:

```ts
// Inside the existing native transaction, after final authorization checks.
await transaction.saveInvocation(invocation);
await transaction.appendActivity([invocationRecorded, ...createdObjectEvents]);
```

These are event drafts: the runtime assigns stable event IDs and semantic
metadata, and the adapter supplies `recordedAt` and publication positions.
`appendActivity` stages drafts within the transaction; it participates in
transaction/savepoint rollback and handle revocation. The adapter publishes
those drafts after the transaction callback succeeds and before COMMIT, so no
user callback runs while holding the publication lock. It is not an independent
store call or an after-commit callback.

- Success records one terminal invocation event plus its committed creations.
- A domain failure rolls back effects and records only its failed terminal
  receipt event in the outer transaction.
- Known rollback produces no committed events.
- Replay produces no new terminal invocation or creation events. It may produce
  a best-effort attempt event with `replayed: true`.
- A lost COMMIT acknowledgement leaves the attempt `uncertain`. If the commit
  succeeded, its durable events already exist. Never turn uncertainty into a
  known rejection or automatically execute the action again.

This describes Relate-owned state. External effects performed by an action are
not made transactional by an activity row.

### Source acceptance

Extend `ObservationStore.accept` with trusted activity provenance (actor,
operation/context, occurrence time and preassigned candidate event ID). Under
its existing acceptance lock, the adapter determines the actual winning
transition and writes the observation, any value history and the structural
activity event together. The runtime owns the event schema; the adapter does not
fetch sources or evaluate authorization.

- First membership acceptance emits `object.adopted`.
- Subsequent accepted mapped-value or present/deleted state changes emit
  `source.change-observed`.
- Unchanged, superseded and replayed observations emit neither. A raw provider
  field change alone does not invent a mapped business-value change.
- Concurrent adoption/refresh uses the winning accepted state, not a diff
  computed outside the transaction. A repeated acceptance does not duplicate the
  event.
- The history ID refers to the row actually written, when one exists.

An initial adoption is one adoption event, not a duplicate change event. Memory
and Postgres must agree on metadata event semantics; memory need not gain value
history solely for activity. An absent history reference means no exact
historical payload is available through that event.

If required activity persistence fails, observation acceptance fails atomically
using the existing retention failure/uncertainty contract. Whether the enclosing
read can return freshly fetched data is still governed by its existing evidence
and retention semantics; activity must not silently claim confirmed retention.

## Recording access activity

Access capture uses a bounded queue with limits on entries, bytes and concurrent
writes. It never awaits delivery on the consumer result path. The runtime
isolates synchronous store throws and rejected promises. It does not claim
literally zero latency or resource overhead.

Provide access-recording configuration, drop counters and a host error hook.
Queue overflow, write failure and shutdown abandonment are observable without
trying to report them only through the failing activity store. Diagnostics use
sanitized failure codes and event types, not raw exception messages, IDs or
values. Callback failures must not affect operations.

A hung append occupies at most the configured concurrency; do not create
unbounded retries or new writes. Store implementations must support bounded I/O
or cancellation that releases resources. Best-effort traffic must not exhaust
the pool required by committed writes. Retry, if provided, reuses event IDs;
append of identical IDs/payloads is idempotent and conflicting reuse rejects.

`close()` first drains tracked operations, then drains access capture with an
explicit activity flush deadline. The existing Node close implementation has no
such deadline; adding it is implementation work. Deadline expiry reports
abandoned capture and must not close a host-owned shared store. Specific default
queue sizes and flush duration are implementation choices, exposed and tested.

## Storage and table changes

Keep the capability on the existing store composition rather than introducing a
second independently committed database:

```ts
interface ObservationStore {
  readonly native?: NativeStore;
  readonly activity?: ActivityStore;
  // Existing observation operations; accept gains activity provenance.
}
```

Built-in memory and Postgres stores implement activity. Third-party adapters may
omit it, but an adapter advertising activity must support the atomic source and
native guarantees for every write capability it exposes. A standalone
best-effort sink cannot advertise that guarantee. Runtime setup validates the
capability combination. Events have the durability of their owning store.

| Table                | Proposed additions/responsibility                                                              |
| -------------------- | ---------------------------------------------------------------------------------------------- |
| `native_objects`     | `created_by_invocation_id`; retain object values and creation time                             |
| `native_invocations` | `recorded_at`, `definition_revision`, `operation_id`; retain replay and authorization evidence |
| `objects`            | Current source observation and identity, unchanged ownership                                   |
| `value_changes`      | `activity_id` linking new history rows to metadata events                                      |
| `activity_streams`   | Graph stream identity, last committed position and retention floor                             |
| `activity`           | Versioned metadata entries plus indexed filter columns and publication position                |
| `activity_objects`   | Typed, role-bearing references for object filtering                                            |

Provenance additions remain nullable for legacy rows only. Activity links do not
make deleting an activity entry delete receipts, objects or value history.
History links are references, not cascading ownership. Physical migration must
preserve existing idempotency keys and authorization evidence.

The core Postgres keys are:

```sql
-- activity_streams: one transactional counter/retention record per graph.
PRIMARY KEY (graph_id)

-- activity: identity is separate from publication order.
PRIMARY KEY (graph_id, id)
UNIQUE (graph_id, position)

-- activity_objects: graph scope is enforced by the foreign key too.
PRIMARY KEY (graph_id, activity_id, object_type, object_key, role)
FOREIGN KEY (graph_id, activity_id)
  REFERENCES relate.activity(graph_id, id) ON DELETE CASCADE
```

`activity` stores the full entry as JSON plus adapter-derived columns for graph,
position, event type, actor kind/ID, occurrence time, action, invocation,
request and operation. Index graph/position and the supported filter paths;
object lookup indexes graph/object type/object key/activity ID (and role where
useful). The adapter validates duplicated columns against the entry and inserts
references atomically. Events are immutable except explicit retention/erasure
operations.

### Publication order

For the first Postgres implementation, allocate positions from a transactional
per-graph counter row, holding its lock until commit. Allocate the batch and
insert its events together as the final database work, after domain validation
and without provider I/O or user callbacks under the publication lock. Every
writer, including access capture, follows this protocol and consistent lock
ordering. Memory implements the equivalent atomic append.

This ensures that no earlier position can become visible after a later committed
position has been returned. A rolled-back transaction exposes neither its events
nor its counter update. Do not replace this with UUID ordering or a bare SQL
sequence: allocation order alone does not establish commit visibility order. The
publication lock serializes a short final section per graph, which is an
explicit throughput tradeoff to measure before considering a different
publisher.

The retained activity log also supplies outgoing delivery; no separate outbox or
broker is required for this first implementation. A future exporter stores its
own checkpoints/delivery state outside event rows.

## Host reading contract

Filters, pages and errors are transport-safe protocol types. Storage interfaces
in `relate` consume them, so future HTTP clients need not depend on runtime
code.

```ts
interface ActivityFilter {
  readonly actor?: ActivityActor;
  readonly types?: readonly ActivityEntry['type'][];
  readonly objectDefinitionId?: string;
  readonly object?: ActivityObjectRef;
  readonly objectRole?: EntryBase['objects'][number]['role'];
  readonly actionDefinitionId?: string;
  readonly invocationId?: string;
  readonly operationId?: string;
  readonly requestId?: string;
  readonly from?: string; // Inclusive occurredAt, RFC 3339.
  readonly to?: string;
}

interface ActivityPage {
  readonly entries: readonly ActivityEntry[];
  readonly nextCursor: string;
  readonly hasMore: boolean;
}

interface ActivityReader {
  status(): Promise<
    | { readonly state: 'unsupported' }
    | {
        readonly state: 'available';
        readonly durability: 'volatile' | 'persistent';
        readonly accessRecording: 'enabled' | 'disabled';
      }
  >;
  list(options?: {
    filter?: ActivityFilter;
    cursor?: string;
    limit?: number;
  }): Promise<ActivityPage>;
  read(options?: {
    filter?: ActivityFilter;
    cursor?: string;
    limit?: number;
  }): Promise<ActivityPage>;
}

// Store methods additionally take graphId; the host reader binds its graph.
interface ActivityStore {
  appendAccess(
    graphId: string,
    entries: readonly AccessActivityDraft[],
  ): Promise<void>;
  // status(graphId), list(graphId, options), read(graphId, options)
}
```

`AccessActivityDraft` is the read/attempt/receipt subset without store-assigned
recording time; committed events cannot enter through `appendAccess`.

- `list` returns newest publication first. Its first page pins an upper position
  so subsequent pages are stable against new appends. It is timeline browsing,
  not chronological sorting by occurrence time.
- `read` returns oldest publication first, starting at the retention floor when
  no cursor is supplied. Thereafter it returns every matching retained event
  after the checkpoint. A finite call reads to a captured committed high-water
  mark; consumers poll again to follow new appends.
- Cursors are opaque, validated and bound to graph, stream identity, direction
  and normalized filter. Changed filters or a cursor from another graph/method
  reject as `invalid-cursor`. Limits default to 50 and range from 1 to 500. A
  resumed call inherits its cursor's filter when none is supplied.
- `nextCursor` describes the range scanned, including filtered-out entries. An
  empty filtered page can advance it. Never advance past unreturned matching
  events; `hasMore` tells whether more matches remain in the call's range.
- `objectRole` requires `object` or `objectDefinitionId`. Filters combine with
  AND; types within `types` combine with OR. Reject contradictory object and
  object-definition filters. All references match within the bound graph.
  Object-definition filtering matches typed references and a read's result
  definition even for an empty page; a role filter requires a matching
  reference.
- Re-reading a checkpoint may return duplicates; consumers deduplicate using
  event identity and checkpoint only after successful processing. There is no
  exactly-once external side-effect guarantee.
- Unsupported activity rejects reads as `unsupported`, not an empty history.
  Store failures are `unavailable`, malformed options are `invalid-request`.
  Expired/lost stream positions are `cursor-expired`.

### Retention and restart

Memory retains the newest 10,000 entries per graph, with a byte bound as well.
Eviction removes a contiguous publication prefix and advances a retention floor.
A new memory store has a new stream identity; its old cursors expire. Bound
individual events as well as buffers: access events that exceed the limit are
dropped and counted rather than silently truncating an audit claim; oversized
committed event batches reject the associated transaction.

Postgres initially retains entries until an explicit trusted pruning operation.
Pruning removes a contiguous prefix, including object index rows, and advances
the floor atomically. It never resets/reuses positions or changes stream
identity on an ordinary restart. A cursor behind the floor fails explicitly; it
must not silently skip deleted events. Consumers then rebuild their own
projection or explicitly choose to resume from retained history. Historical
detail can expire independently; resolving a missing history reference must
report that absence.

Read each page, its high-water mark and its retention floor from one consistent
snapshot so concurrent pruning cannot create an undetected gap. Access append
deduplication is guaranteed while the entry is retained; access retries must be
bounded to that retention window rather than resurrecting pruned history.

Automatic retention schedules and subject-specific erasure require separate
policy design. Append-only describes normal recording, not a promise that data
can never be removed. Detailed prune authorization/options are implementation
API work; the retention-floor and expired-cursor contract is required now.

## Third-party applications and data access

Only trusted host code and the Inspector can read activity initially:
`runtime.host.activity` implements `ActivityReader`. No activity methods are
added to `as(user)`, `ConsumerOperations`, MCP tools or consumer HTTP routes.

Metadata supports notifications, timelines, cache invalidation and triggering an
authorized refresh. Fetching an object after an event returns its current state,
not necessarily its event-time state. Exact historical applications need a
retained history reference and a separately authorized history API. A reference
or activity event never grants permission to its payload.

Before remote exposure, define integration credentials, graph/event scopes and
field projections. Current permission to read an object does not automatically
authorize its access history. Per-user feeds need explicit historical visibility
rules. Do not export trusted raw events indiscriminately.

A later export adapter maps entries to CloudEvents: a stable installation/graph
URI becomes `source`, entry ID becomes `id`, event type becomes `type`,
occurrence time becomes `time`, and the versioned selected metadata becomes
`data`. Installation identity must distinguish independent deployments that use
the same graph ID. Preserve source/ID across retries. CloudEvents supplies an
interoperable envelope, not persistence, ordering or delivery guarantees.

Primary references verified on 2026-10-13:

- [CloudEvents 1.0.2](https://github.com/cloudevents/spec/blob/v1.0.2/cloudevents/spec.md):
  envelope and source/ID duplicate identity; optional boundary mapping, not a
  runtime dependency.
- [PostgreSQL sequence semantics](https://www.postgresql.org/docs/18/functions-sequence.html):
  sequence allocation is independent of transaction rollback; it is not the
  publication protocol.

## `relate dev` and the Inspector

1. The dev server passes context and operation identity through IPC to the
   runtime host. The runtime captures graph results and committed events.
2. After committed publication, the runtime host forwards entries to the dev
   server: `{ type: 'activity', runtimeId, entries }`. Forwarding is best effort
   and never part of the native/source transaction. A feed reader can recover
   committed entries if immediate forwarding misses an acknowledgement.
3. The dev server deduplicates by graph/event ID and retains a bounded display
   history across runtime-host restarts. It is a development projection, not a
   durable integration checkpoint or a replacement for the store's feed.
4. L1 calls and L2 agent executions remain dev-server events and join by request
   and execution IDs. The Inspector renders the new event families in place of
   L3, distinguishing committed changes, attempts and uncertain outcomes.
5. Delete `packages/cli/src/dev/activity/operations.ts` when runtime capture is
   connected. Keep only explicit pre-dispatch rejection capture at the routing
   boundary. Development progress/running indicators can remain transient UI
   state; they do not mutate immutable persisted entries.

Losing a memory runtime can still lose unforwarded volatile events. Retaining a
dev-server display across saves is not a durability guarantee.

## Ownership and implementation sequence

| Location                                              | Responsibility                                                                   |
| ----------------------------------------------------- | -------------------------------------------------------------------------------- |
| `packages/protocol/src/activity.ts`                   | Context, event union, filters, pages, status and reader errors                   |
| `packages/relate/src/storage.ts`                      | Activity store capability; atomic native append and source acceptance provenance |
| `packages/runtime/src/activity/`                      | Event construction, per-operation context, access queue and diagnostics          |
| `packages/runtime/src/actions/`, source resolution    | Emit drafts at native and observation commit boundaries                          |
| `packages/runtime/src/memory.ts`, native memory store | Atomic metadata recording, bounded retention, stream/cursor semantics            |
| `packages/postgres`                                   | Migrations, provenance links, transactional publication, indexes and pruning     |
| `packages/node/src/runtime.ts`                        | Host reader, binding context, capture configuration and bounded activity drain   |
| `packages/cli/src/dev/`, `apps/inspector`             | IPC/projection integration, pre-dispatch attempts and rendering                  |
| `tests/support/activity-store-contract.ts`            | Shared memory/Postgres guarantees and recovery cases                             |

Protocol remains portable; runtime depends on authoring/storage contracts, Node
composes runtime, and Postgres implements storage contracts. Inspector consumes
protocol types. Exporters consume the host reader rather than importing SQL or
becoming dependencies of runtime writes.

Implement storage/protocol guarantees first, then runtime capture, then host
reading and Inspector integration. Public docs and store contracts must be
updated with the implementation; this design is not proof of shipped behaviour.

## Acceptance tests

- Creation, receipt and activity commit together; injected event-write failure
  rolls them all back. A failed domain action records its terminal receipt but
  no rolled-back creations. Savepoint and revoked-handle behaviour is preserved.
- A crash after COMMIT but before response/forwarding leaves events recoverable
  from Postgres after restart. Lost acknowledgements produce `uncertain`
  attempts while committed events remain authoritative.
- Concurrent idempotent invocations execute once; replay adds no change events.
  Event append retries deduplicate identical IDs and reject conflicting reuse.
- Source adoption/value changes and events commit together, concurrent refresh
  losers emit nothing, unchanged/raw-only changes emit nothing, and retained
  history links identify the actual accepted row. Memory/Postgres event
  semantics agree without requiring memory value-history storage.
- Reads capture stable property IDs and distinguish forbidden/unavailable;
  compact/full evidence modes produce equivalent activity. Hidden and missing
  gets retain the same requested target and indistinguishable outcomes.
- Query/internal reads do not over-report delivered objects. Traversal origins
  retain their own object-definition identity. No values, inputs or raw errors
  appear in any activity event or capture diagnostic.
- Access write rejection, synchronous throw, hanging I/O and queue overflow do
  not change consumer results; resource bounds and drop diagnostics hold.
  Shutdown drains operations before bounded activity flushing.
- Many calls through one embedded binding get distinct default request and
  operation IDs. Transport-bound calls share request context but have distinct
  operation IDs. Retired routing records exactly one pre-dispatch attempt.
- Delay an earlier writer while a later writer runs: advancing a feed checkpoint
  cannot skip an event that commits afterwards behind it. Run this with multiple
  Postgres connections, rollback, mixed source/native/access writers and
  restart.
- Catch-up larger than one page returns all matches in order. Empty filtered
  scans advance safely; cursor graph/filter/direction binding rejects misuse.
  New writes do not disturb pinned descending browse pages.
- Memory eviction, explicit pruning and stream replacement expire affected
  cursors explicitly. Persistent restart preserves valid cursors and event IDs.
  Unsupported, unavailable and genuinely empty activity remain distinguishable.
- No consumer surface exposes trusted history. Inspector joins runtime events
  with L1/L2, deduplicates forwarded entries and preserves its bounded display
  history across runtime-host restarts.
